# 2026-08-04 — Boat work is back, and so is the switch — in Settings, on a new key, defaulting to land

> *"In a previous session, we disabled the Boat work because it wasn't getting used —
> however, it is gonna get used today. So instead can we move the boat toggle into the
> settings, and then also the default should be land mode in case that wasn't clear."*

## The switch comes back, two taps behind ☰

[Four days ago](2026-07-31.md) the Boat/Land switch was removed from the capture page's
top bar and `workMode()` was hard-forced to land. The reasoning then was that boat work
had wound down, so the control could only ever be set *wrong*: one accidental tap in a
moving truck gave the crew the boat daily-log template, the "Departure time (left dock)"
labels, and `workType:'boat'` on every write for the rest of the day.

Boat work is running again today, so the mode has to be settable — but that objection
never depended on boat work being over. A mode a crew changes a few times a year does not
earn a permanent slot next to the sync pill. It is now **Settings ▸ Work mode** (☰ ▸ ⚙︎),
a two-up Boat/Land pill sitting between "Who are you?" and "Offline road map". It saves on
tap rather than behind the Save button — matching `tuneShowDriveMetrics`, the other
device-local preference — and it is sticky: set it once in the morning, it survives
reloads until someone sets it back.

`LOCKED_MODE` is deleted outright rather than set to `null`. A dead constant naming the
lock is a re-lock waiting to happen, and it was cited by three files.

## The key had to be renamed, or every phone would have come up boat

This is the part worth remembering, and it is the same trap the July entry described from
the other side.

Boat was the **original** default, under `localStorage['workMode']`, back when the read was
`=== 'land' ? 'land' : 'boat'`. So every phone in the field carries a literal
`workMode='boat'` — not an absent key, a real stored string. The July lock rescued those
phones by *ignoring* the key rather than clearing it.

Which means "make the default land" does nothing on its own. A default never fires on a key
that is already set, so re-reading `workMode` with a land fallback would have brought most
of the fleet up in **boat** on the first load — the exact opposite of what was asked for,
and invisible until someone noticed their screen was blue.

So the mode moved to a fresh key, `captureWorkMode`, which is what makes "unset ⇒ land"
mean anything. The legacy key is abandoned rather than migrated: swept once on load so a
phone's localStorage dump can't mislead the next person debugging a mode report, and never
read again. The polarity flips with it — the read is now `=== 'boat' ? 'boat' : 'land'`, so
an absent, blank or hand-mangled value all resolve to land.

The boot path is `applyModeUI(); paintModeSeg();`, deliberately **not** the pre-lock
`setMode(workMode())`. That old line wrote the key back on every single load, which is
precisely how a default that was only ever meant to be a fallback ended up baked into every
phone in the fleet as a literal value. Reading must not write.

## The bug the lock had been hiding

With the mode frozen, one path had been unreachable for four days: `eodStateKey()`
fingerprints everything the end-of-day summary depends on — the gap allocations, both
bookends, the notes, the include-delays checkbox — but not the work mode. And the mode is
what picks the PDF template.

So: open End of day (which kicks off `prefetchEodSummary`), walk to Settings, flip the
mode, come back and tap Finish. The state key still matches, the cached summary is adopted,
and the crew gets a **land PDF for a boat day** with no error anywhere. Two independent
guards, because this one fails silently: the mode is appended to `eodStateKey()`, and
`setMode()` drops `eodServerSummary` outright.

Three other mid-flip behaviours were checked and deliberately left alone, each documented
where it lives:

- **A gap list already on screen** is not rebuilt. `computeGapsLocal` prepends a
  zero-length lead gap in land only, so a list built under the other mode has one row too
  many or too few — but re-running `loadDay` mid-review would discard deductions the
  installer has already typed. Closing and reopening End of day rebuilds it.
- **A drive leg in flight** keeps the mode it started in. `startSegment` stamps `workType`
  once and `resumeSegment` reads it back off the persisted row. There is no honest answer
  for a leg spanning a change.
- **Rows already queued** keep the mode they were logged under. A stop logged at 9am on
  land must stay land even if the phone flips at noon — which is why the Settings copy says
  to set it in the morning, and why a mid-day flip splits the day across the `boat*`/`land*`
  column groups in `InstallerMetrics`.

## What did not change

No data-model change, again: `workType` already rode every payload and its appended-last
columns on `Stops`/`Downtime`/`Tracker`, `normWorkType` already read blank as boat, and
`js/dailylog.js` never lost the boat template. Every boat code path below the UI stayed
live through the lock, which is why turning the switch back on was a UI change and a key
rename rather than a restoration.

`teams.html` keeps its own view switch on `teamsViewMode`. Now that *both* pages have a
switch again the separate key matters more, not less — it is the only thing stopping an
admin flipping the office view to Boat from repainting a crew's phone and retagging their
day. Two stale comments there (and one in `css/tokens.css`) asserted the capture app was
locked; all three now say why the keys stay apart instead.

The three `installerMetrics` reads that hardcode `workType:'land'` — `js/worklist.js`,
`js/worklist-tuning.js`, `js/pages/planner.js` — are still hardcoded. Route planning is a
land workflow whatever the capture screen is set to; that predates the lock and is not an
oversight. It is now pinned by a test, since it is exactly the kind of thing someone would
"finish the job" on.

`tests/work-mode-lock.test.mjs` becomes `tests/work-mode.test.mjs`: six of its seven tests
asserted the *absence* of the switch and invert. The Settings-sheet placement is checked
positionally (`#settingsSheet` < `#modeBoat` < `#downtimeSheet`, and no `mode-seg` in the
top bar) — a bare "index.html contains modeBoat" would pass if someone put it straight back
on the bar, which is the whole thing July was about.
