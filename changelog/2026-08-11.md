# 2026-08-11 — The SSD bundle's restore script comes home, and it no longer assumes CH

`scripts/setup-geo-on-new-pc.ps1`, `DEPLOY.md`

The planner came up with both readiness badges offline and the report was that its
*files* had been deleted. They hadn't: `planner.html`, `css/planner.css`,
`js/pages/planner.js`, `js/planner-services.js` and all 18 modules in the import graph
were present, every `sw.js` `SHELL` path resolved, and `git status` was clean. What was
gone was **Docker** — `Images=0, Containers=0, Local Volumes=0` on a healthy engine — so
OSRM (`:5000`) and Nominatim (`:8080`) simply didn't exist any more, which the badges
report exactly as designed. Worth writing down because the symptom points at the wrong
half of the system: the planner is a thin client over two local services, and losing the
services looks identical to losing the page.

## The repo's copy of the restore script had drifted out of date

Recovery should have been one command, because `F:\geo-bundle` survived with both images
(`nominatim-ontario.tar` carries the imported Postgres DB *inside* the image, which is why
it is 5.3 GB and why the DB cannot simply be restarted after a wipe — it has to be
reloaded). But the two copies of the setup script had diverged: `git log --follow` shows
the repo's was committed once in `7ef68a8` and never touched again, while the copy living
on the SSD had been fixed during a real setup on an ARM64 machine and never carried back.
This is precisely the drift `CLAUDE.md` was written about, one directory over.

The repo copy is now the SSD copy (BOM stripped, LF endings per `.gitattributes`). Five
differences, of which the first is the one that bites:

- **`--algorithm ch` was hardcoded.** OSRM has two preprocessing pipelines and the run
  flag must match the data: `osrm-contract` writes `<base>.osrm.hsgr` and pairs with
  `ch`; `osrm-partition` + `osrm-customize` writes `.partition`/`.cells`/`.cell_metrics`/
  `.mldgr` and pairs with `mld`. `D:\osrm` holds the **MLD** set and no `.hsgr`, so the
  repo's script would have started a container that fails to load the graph and exits
  seconds later. It now tests for `.hsgr` and picks the algorithm to match.
- Containers get `--name osrm-ontario` / `--name nominatim`, so a re-run can actually
  replace them (the unnamed originals left `docker rm -f` nothing to match).
- An ARM64 host builds `arm64-patch\` first — the amd64 Nominatim's apache2 dies under
  QEMU emulation, so that variant serves the same baked-in DB through the Python API
  server instead.
- The engine check reads `$LASTEXITCODE` rather than wrapping `docker info` in
  `try/catch`, which never fired: a native exit code doesn't throw.
- It polls both endpoints before claiming success instead of trusting `docker run`.

**Trap worth remembering:** that last one produced a *false negative* on this very
restore. Both waits timed out — 180 s for OSRM, 600 s for Nominatim — and both containers
were nonetheless healthy; the 5.3 GB image load and the OSRM data copy had saturated the
disk, so the MLD graph was still loading when the clock ran out. `docker ps` showing `Up`
and OSRM's `running and waiting for requests` are the real signal. `DEPLOY.md` now says
so, because "setup finished, but not everything came up" is exactly the message that
invites someone to start tearing down a working install.

A second trap cost time before the restore even began: **an unrelated app was holding
port 5000**. `Salad.Bowl.Service` had a Kestrel server on `127.0.0.1:5000` answering the
planner's probe with a bare 404 — which reads as "offline" on the badge and would also
have blocked the container from binding. A badge that is offline while `docker ps` looks
fine is worth one `netstat -ano | findstr :5000` before anything else.

## `DEPLOY.md` gains the pairing rule and a recovery section

The from-scratch OSRM instructions were never wrong — they tell you to run
`osrm-contract`, which *does* yield `.hsgr` for `ch` — but nothing in them mentioned MLD
or that the two halves must agree, so the data actually on this machine and the documented
run command disagreed silently. The pairing rule now sits next to the `osrm-routed`
command. The SSD-bundle section gains an explicit note that the same bundle is the
recovery path when Docker is wiped on the PC that already worked, with the
`-OsrmData D:\osrm` form that reuses the graph already on disk instead of copying a
second set to `C:\osrm`.

## Verification

`node --test "tests/*.test.mjs"` — 637/637 green (the suite includes assertions over doc
content, so the `DEPLOY.md` edit is covered). Services confirmed by hand rather than by
the script's own summary: OSRM returns `code=Ok` with an asymmetric distance matrix
(`[[0, 14355.6], [24561.4, 0]]` — real road routing, not straight-line), Nominatim
resolves *Bracebridge, ON* and reports `status:0 OK` from `/status?format=json`, which is
the endpoint the badge actually probes. Then driven end-to-end in headless Edge
(`VERIFY.md` §3) against the served page, since curl proves nothing about CORS: both
`#plOsrmStatus` and `#plGeoStatus` render `provider-status online` reading **Online**, the
map draws, and the spine pill reads Synced. No app code was touched — the planner's own
files were never the problem.
