# 2026-07-31 — The day is settled when the installer says it is: a 🔓/🔒 work-list lock, and the road button stops answering with the whole week

> *"I'm continuing to have issues with the way work lists are locked, so I would like a
> toggle switch which unlocks the work orders on the work list — which unlocks the day
> and the target. If I leave the toggle to unlock, I can set my target and I can set the
> date, and when I press optimize the route that will be created will follow the target.
> The moment I press lock it will lock the work list to that target for the day … so it
> won't shuffle work lists up or down until I unlock it manually and re-optimize. The
> exception is if I lock it and I add a work order to the list — that's when I'll get
> prompted with the same existing message of where I'd like to place it."*

Yesterday's entry ends with a table of five scenarios and the sentence *"the manual ask
still works"*. This is the fourth change in a week to the same question — which orders
are on today — and each one has been a correct fix to a real report. That is the tell.
The mechanism was never wrong in a way one more case could patch; it was answering a
question it could not observe.

## The thing that kept going wrong was the inferring, not any of the inferences

`js/route-today.js`, `js/worklist.js`, `js/route-planday.js`

The today anchor froze Day 1 automatically, so it had to work out *when the installer
meant to re-plan* from whatever it could see. By yesterday that was:

- `needsCommit`, with four reasons to re-freeze (a new day; an exhausted set; an
  explicit re-plan; a re-plan whose meters/day target had moved);
- `dayCapacity`, bounding how far a mid-day target raise could grow the day;
- `freshAnchorIds`' `opts.max` (that bound) and `opts.fromTags` (are the `day` tags
  fresh enough to describe the target being frozen at?);
- and a `freeReplan` / `midReplan` / `exhausted` triangle inside `applyTodayAnchor`,
  plus a `capacity === 0` skip guarding against freezing an empty set.

Every line of that is defensible on its own and the whole is not answerable from the
truck. The installer's two questions are **is my day settled right now** and **what do I
press to change it**, and no arrangement of inferred state answers either one.

So they say. One control, above 🧭 Optimize:

| | 🔓 unlocked | 🔒 locked |
|---|---|---|
| Optimize | re-plans everything at the target | re-solves the geography; day 1's **membership** is untouched |
| Meters/day | sizes every day, live | read-only, showing the number the day was settled at |
| Planning for | free | read-only |
| A logged stop / Download / the 5-min refresh | re-times only | re-times only |
| Adding an order | just takes its place | asks: **Add to today** / **Leave for later** |

`needsCommit`, `dayCapacity`, `opts.max`, `opts.fromTags`, `opts.replan`, `opts.resize`
and the triangle are all **deleted**. The press is the only commit there is.

## The lock is one date, which is most of why it is simple

`js/worklist.js` `dayLocked()` / `setDayLocked()` / `releaseStaleDayLock()`

`localStorage['wlDayLock']` holds a `yyyy-MM-dd`; the list is locked **iff it equals the
day being planned**. That single equality gives the auto-release the installer asked for
— a lock is a statement about one day's work, so Tuesday's means nothing on Wednesday —
with no timer, no expiry sweep and nothing to get wrong at midnight. Blank is unlocked.

The frozen *set* stays where it was, in `wlTodayAnchor` `{date, ids, target}`, written
once at the press by `freshAnchorIds` — which takes the route's current lowest-`day`
group, because that is literally what is on the screen the installer is looking at when
they decide the day is right.

## Unlocked cannot mean "no `day1Count`" — that ships yesterday's bug back

`js/worklist.js` `currentDay1Count()`, `js/route-today.js` `taggedDay1Ids()`

The obvious reading of "unlocked = nothing is frozen" is to pass `day1Count: null` and
let the target chunk the days. That is right for the two deliberate acts and **wrong for
every other caller**, and `applyTodayAnchor` has a lot of other callers: after every
logged stop (`planAdvance`), the Drive screen's 5-minute `autoSync`, Download, and boot.
Re-chunking there would refill Day 1 from the front of `pending` as orders were
completed — an installer who simply had not pressed 🔒 watching tomorrow's orders climb
into today as they worked, on a timer. That is verbatim the report yesterday's entry is
about.

So there are **three** answers, not two:

| | `day1Count` |
|---|---|
| locked | the frozen set ∩ pending, entire (**0 is a real value**, not "unset") |
| unlocked, `opts.rechunk` | `null` — size every day by the target |
| unlocked, passive | the day as currently tagged (`taggedDay1Ids`) |

Exactly one caller passes `rechunk`: the meters/day box, which moved the number without
re-solving, so its `day` tags still describe the old one. **Optimize deliberately does
not** — it rewrites every tag at the new target moments before it calls, so holding them
*is* the fresh split.

Three call sites re-schedule the pending list, not one. `switchVariant` and
`persistOrderIds` (the drag write-back) call `scheduleRouteConstraints` themselves, and
while they omitted the count the lock leaked: flipping road↔straight, or dragging a
single card, silently put Day 1 back to a full target. They read `currentDay1Count()`
now, as does `applyTodayAnchor`.

## Adding an order to a locked day, and the office landing on one

`js/worklist.js` `offerAddTo` / `acceptAddTo` / `adoptPlannerDay1`

The `#wlAddTo` sheet is unchanged in shape — **Add to today** or **Leave for later**,
cheapest-insertion into the day, nothing displaced to make room — but it now appears
only while the list is locked. Unlocked there is nothing to join and nothing to protect,
so the question would have no consequence attached to either answer.

`adoptPlannerDay1` **reverses**. It used to fold the office's whole day 1 into today
without asking — *the planner decides, the phone obeys*. The installer pressed 🔒 on a
day they had looked at, and an office re-plan landing during it is exactly the case the
toggle exists to survive, so the office's extra orders go through the same sheet as a
hand-typed one. Only the manual ⇩ Download raises it: this also runs on `autoSync`,
whose whole contract is that it never speaks, and a modal over the Drive screen at
80 km/h is worse than the staleness it fixes. There the extras stay out of today and
wait for the installer to open the worklist.

## The office gets the same toggle, and one appended column carries it

`planner.html`, `js/pages/planner.js`, `Code.gs`

`WorklistPlans.dayLockDate` (column L, appended last) carries the **date only** — the
frozen membership up there is just the rows tagged `day === 1`, so there is no second
source of truth for the same fact. Three things about it are the kind that fail quietly:

- **Blank is a real value.** `saveWorklistPlan` guards the write on key *presence*
  (`hasOwnProperty`), not truthiness — the one place it differs from `routeStartDate`.
  The truthiness form would make unlocking from the phone a silent no-op on the sheet,
  forever. Same shape as `day1Count === 0`.
- **The phone adopts a lock, never an unlock.** `loadPlanFields` takes the sheet's date
  only when the phone is currently unlocked for that day. This is the *one* downloaded
  plan field it adopts — `target` and `commutePull` beside it are deliberately refused —
  because a lock is not tuning.
- **A lock adopted from the sheet arrives without its set.** `applyTodayAnchor`
  snapshots the day as tagged to repair that, and `currentDay1Count` falls back to the
  tag count in the window before it runs; reading the anchor blind would return 0 and
  collapse Day 1 to nothing.

`setupSheets()` pins L to plain text. A date-formatted cell comes back from
`getValues()` as a **Date**, and this string is compared for equality against the plan
day — it would fail with no error and no wrong number to notice, the exact silent shape
that cost the measured-dwell block its first release.

## Two glyphs, two different jobs

Every order card already carries a 🔒 — the *position* lock, pinning one stop to a date
and slot. The day lock uses the same padlock, so the label does the work: it is a
full-width bar outside any card that always spells out which state it is in
(*"🔒 Work list locked · today's 7 orders are set"*), never an icon on its own. Same on
the planner, where the per-order lock is a 36px square in a row and this one is a
labelled button in the settings card.

`readOnly` on the greyed controls is the **affordance only** — a number input's spinner
and a date input's picker both ignore it on some browsers — so the `onchange` handlers
are the actual guard, reverting the value and saying why.

## Migration

`migrateLegacyLock()` is a one-shot: a phone mid-day when this ships has a committed
anchor for the plan day, which *was* the frozen day before the toggle existed, so it
carries across as an explicit lock. Without it the deploy itself would soften a day the
crew was driving. It is keyed on its own marker rather than on "`wlDayLock` is blank",
because blank is the real unlocked state and migrating off it would re-lock the day on
every reload after an unlock.

The sheet needs no `setupSheets()` run for the header — `WorklistPlans` writes call
`ensureTab()`, which fills the new blank cell — but **one run is needed for the number
format** on column L.

## The road button answers "how far am I driving today", not "how long is the plan"

> *"There's a bug with how much distance the route has — I only have two orders that
> are around 2km away from each other but my driving distance on the road button shows
> 241km+. This distance is supposed to be for the distance on the route, not including
> drive home or from the starting location."*

`js/route-variants.js`, `js/worklist.js`, `js/pages/planner.js`, `js/route.js`, `index.html`

**The number was right and the question was wrong.** Both variant tiles and the counts
line read `241 km (road)` over day headers reading `2.2 km` and `6.3 km`. Nothing was
double-counting a commute: `legMetersFor` has always charged every day's first stop 0,
and the drive out lives in `homeLegMeters*`, which no total reads. The headline was
simply **unscoped** — `variantMeters` sums every pending order's leg across day 1..N —
so one far-off order parked at the bottom of a four-day plan landed in the figure the
crew reads as today's driving.

That is a scope bug, and the fix is a scope, not a subtraction:

- `routeTotalSummary(items, variant, src, {day})` and `variantSummary(items, variant,
  {day})` price a single day. The phone passes `day: 1` — `worklist.js HEADLINE_DAY`,
  Day 1 strictly, the convention `todayPending` already uses.
- **The counts line's scoped metres come from `liveDayMeters`, not `variantMeters`.**
  That is the load-bearing half: it buckets on the *live* `day` field the day dividers
  bucket on, so the headline and Day 1's divider are the same number **by
  construction**. The gap between those two was the entire report; leaving them as two
  independent sums that happen to agree is how it comes back.
- The tiles bucket on each variant's **own** saved day instead, because two saved plans
  put different stops on their first day — comparing each plan's own day 1 is what
  keeps the road-vs-straight choice like-for-like.
- **The office is unchanged and now says so.** Planning the week is what `planner.html`
  is for, so it stays unscoped and passes `{days: true}`: its figure reads
  `241 km (road) · 4 days`. A labelled whole-plan number cannot be misread as one day's
  driving, which is the same bug from the other end.
- The phone gets a caption under the tiles — *"Day 1 only — the whole plan is 241 km
  over 4 days"* (`routeScopeText`, `#wlVariantScope`). A tooltip would have been
  cheaper and useless: there is nothing to hover on a phone, so the number the tiles
  stopped showing had to go on screen or it was gone.
- An empty day prints nothing rather than `0 km` — the same answer the pace card gives
  when today's work is done.

**Two comments were describing code that does the opposite**, and one of them cost this
investigation its first hour. `js/route.js legMetersFor`'s header said *"so a day's
total includes the drive out"* five lines above the branch that charges it 0, and the
worklist's `DAY_KM_TIP` — the tooltip on the very kilometre figure in the day divider —
told the installer the drive out was included. Both now say what the code does. The
planner's equivalent tooltip already did.

**Known and deliberately not fixed here:** setting an order aside (or completing it)
drops *its* leg from the total but leaves the **next** stop's leg, which was measured
*from the stop that is no longer on the route*, and neither `variantCoversPending` nor
`variantMatchesLive` fires — so that figure prints unqualified. It needs re-pricing
rather than re-scoping, and folding it in would have muddied the fix being verified.
It is written down in `ARCHITECTURE.md` §"Route variants" so it is inherited rather
than rediscovered.

554 unit tests pass. Five new cases in `tests/route-variants.test.mjs` pin the scope
rather than the sum, including the reported shape itself: eight orders over four days
with the distant one last, where pushing that order from 229 km to 500 km moves the
unscoped total to 512 km and leaves the day-1 headline at 2.2 km.

Driven headless against the served pages (`VERIFY.md` §3, spine blocked at the browser),
that list seeded straight into IndexedDB:

| surface | before | after |
|---|---|---|
| counts line | `8 remaining · 0 completed · 241 km (road)` | `8 remaining · 0 completed · day 1: 2.2 km (road)` |
| both tiles | `241 km (road)` | `2.2 km (road)` |
| caption | — | `Day 1 only — the whole plan is 241 km over 4 days` |
| Day 1 divider | `2.2 km` | `2.2 km` — unchanged, and now the headline agrees with it |
| planner | `241 km (road)` | `241 km (road) · 4 days` |

## The Drive screen refreshes every 3 minutes, and times your arrival from where the truck actually is

> *"On the Drive page, on the automated sync that happens every five minutes, can we do
> two new things. First thing is change it to every three minutes. Second thing, can we
> use my current location to the next work order as a reference point for an accurate
> ETA."*

Two asks, and the second one is the interesting half.

**Three minutes.** `AUTO_SYNC_MS` in `js/drive.js` and `PACE_REFRESH_MS` in
`js/worklist.js` both move 5 → 3 min. They have to move together — two periods would be
two clocks disagreeing about how fresh "fresh" is, which is why they were tied in the
first place. The 30-second tick is unchanged: it is retry granularity, not the period, so
a tick landing while the driver is in Google Maps still costs 30 seconds of staleness
rather than a whole further period, and at 3 minutes it is still a sixth of it. The cost
is one extra `worklist` + `range` GET per hour, and only while all three gates hold
(tracking armed, *Show driving stats* on, the screen in front).

**Where the next drive starts from.** Every remaining ETA is `scheduleRouteConstraints`
walking `arrival = previous departure + drive`, so the whole day hangs off one question,
and the answer was `lastDonePin` — the pin of the last order the crew **completed**,
falling back to the muster point. That is exactly right standing in a driveway and wrong
in the two cases that matter most in a truck: mid-drive between two houses, and after a
walk-up or any stop that never matched a worklist order (`markWorklistDone` never sees
those). Meanwhile `js/drive-recorder.js` had been `watchPosition`-ing the whole time and
simply never let the coordinates out of the module.

So `lastFix()` now exposes the newest point of the live leg, and `estimateTravel`'s origin
becomes a three-rung ladder — **live fix → last completed pin → muster point** — each rung
reached only when the one above has nothing to say, all three still inside the
`planDay() === localDate()` guard. Driving the real screen with two seeded positions and
otherwise identical data: standing 200 m from the first stop the ETA reads **08:59**;
60 km away it reads **11:08**. Same list, same clock, 2 h 9 min of difference, all of it
the position.

**The two-minute bound is the feature, not a tuning knob.** A web app gets no GPS in the
background, so a Google-Maps hand-off freezes that newest point at the driveway the crew
pulled out of — and it stays there, looking like a perfectly good fix, for the entire leg.
Unbounded, a "current location" origin would be *most* wrong precisely while the driver is
driving, which is the one moment it exists for. `LIVE_FIX_MAX_AGE_MS` makes it decay back
to `lastDonePin` instead. Two minutes is ~3 km at highway speed, inside the ±30% that
`ROAD_DETOUR_FACTOR` already carries; five would be ~7 km and would dominate the estimate.

`routeTravel` re-prices the **first** pending leg from the same fix, because its saved
`legMeters` is the drive from the previous stop *in route order* — anchoring the ETAs on
the truck and leaving that alone would put an arrival time measured from the truck beside
a *Route done ~* clock whose first leg starts somewhere else. Only the first: the rest
really are stop-to-stop and their saved road distance beats anything crow-flies offers.

**And the Drive card now shows it.** `Arrive ~11:08 · in 129 min`, under the address on
the current-order card and on the locked *Driving to* one. It renders the order's own
persisted `scheduledEta` rather than computing a drive time here — the stored field is
already anchored on the fix, and re-deriving it would be a second model of the day that
can disagree with the first. It honours both staleness flags: `~` while the times are
estimates, greyed and labelled `(stale)` when the last solve failed, since this is the
screen the crew actually navigates by and the last place a stale time may look current.

Two things worth keeping:

- **`lastFix()` is a sibling of `liveMetrics()`, not a fifth field on it.** That return
  shape is a HUD contract `paintMetrics` and `routeTravel` both destructure and
  `tests/pace-live.test.mjs` pins. A position is not a metric.
- **`now` is Toronto-pinned** — `hhmmMin(clockOf(stamp()))`, the same expression
  `day1DepartTime` uses. `scheduledEta` is a Toronto clock string, so the first cut's
  `new Date().getHours()` compared two different zones and the `· in N min` half simply
  never appeared. It would have worked on every phone set to Toronto and failed silently
  on any that was not; it was caught only by driving the real screen in a UTC container.

A phone that never armed drive tracking reaches none of this and behaves exactly as it
did before — no location prompt, no GPS wakeup of its own, nothing on screen.

Files: `js/drive.js`, `js/worklist.js`, `js/drive-recorder.js`, `js/route.js`
(`ROAD_DETOUR_FACTOR` exported), `js/route-today.js`, `css/drive.css`, `index.html`,
`USER-GUIDE.md`, plus `tests/drive-eta-origin.test.mjs` and the period assertions in
`tests/drive-auto-refresh.test.mjs`, `tests/pace-live.test.mjs`,
`tests/worklist-day-frozen.test.mjs`.

## The Boat/Land switch comes off: the app is land, and there is nothing to set

> *"Right now there's two different modes on the app … Now it should default to the
> land mode, and right now the boat work is coming to an end and nobody on the boat is
> using the app, so I would like to hide or grey out the toggle switch so you can't swap
> between the two."*

`js/work-mode.js` (new), `js/pages/capture.js`, `js/drive-recorder.js`, `index.html`,
`help.html`, `css/capture.css`

The Boat/Land segmented switch has sat in the capture page's top bar since
[2026-07-18](2026-07-18.md). With nobody running the app from a boat it is a control
that can only be set wrong — one accidental tap and the crew gets the boat daily-log
template, the *Departure time (left dock)* labels, and `workType:'boat'` on every write
for the rest of the day. So it is gone from `index.html`, and `workMode()` moved into
its own module returning `LOCKED_MODE`.

**Forcing the value is the whole change; defaulting to land would have done nothing.**
Boat *was* the default, and the default was reached by "anything not exactly `'land'`",
so every phone in the field has a literal `workMode='boat'` sitting in localStorage. A
new default never consults a key that is already set. With the switch removed, changing
the default alone would have left every existing phone on boat with no way back — the
one outcome worse than the switch. `workMode()` ignores the stored key outright, so a
phone last left on boat comes up land on its next load with nobody touching anything.

**The lock lives in a module of its own because of one import edge.**
`js/drive-recorder.js` was the second reader of the raw key (`workType: store.get(
'workMode') === 'land' ? 'land' : ''`) and it *cannot* import `capture.js`, because
`capture.js` imports **it**. Left as it was, every drive leg would have kept shipping a
blank `workType`, which the spine's `normWorkType` reads as boat — a locked-to-land app
quietly writing boat rows to `DriveTracks` all day. `js/work-mode.js` is the shared
bottom of that dependency, and both now read it. It is a **hard** import of both, so it
is in the `sw.js` SHELL with a comment saying why: absent, the capture page does not
open offline at all.

Nothing about the data model moved. `workType` still rides every payload and still
occupies its appended-last column, the spine still reads blank/`'boat'` on historical
rows, and `js/dailylog.js` keeps the boat template — an old boat day has to keep
reprinting correctly from `edit.html`. The module header carries the four-step revert
recipe (`LOCKED_MODE = null`, the `.mode-seg` markup, the `.mode-seg` CSS, the two
`<head>` snippets), because reconstructing it from a diff months from now is exactly the
work a comment is cheaper than. `applyModeUI()` is deliberately **unchanged** and still
branches on `workMode()`, so lifting the lock needs nothing from it.

### The teams page keeps its switch, on a key of its own

`teams.html`, `js/pages/teams.js`

The office still has to reach historical boat teams, so the admin page's switch stays —
but it was writing the *same* `localStorage['workMode']` the crew's phone read. That was
already a latent oddity and the lock makes it a live one: an admin flipping to Boat to
look something up would repaint a crew phone blue while the app underneath it was land.
It moved to `teamsViewMode` (defaulting to land, where the work is), and `workMode()`/
`setMode()` there are renamed `viewMode()`/`setViewMode()` so the next reader doesn't
mistake a view filter for the app's mode. The markup defaults moved to the land copy
too, or the page flashes *Boat Teams* before the module runs.

## The arrival time on the Drive card was measured in straight lines

`js/route.js`, `js/worklist.js`, `js/roadgraph.js`, `js/roadpack.js`, `js/worklist-route-view.js`

> *"When displaying the ETA on the pace card and the address card on the Drive page, is
> the ETA using the straight line to determine the ETA or is it using road data? I would
> like it to use the road data. I've noticed it's been pretty off."*

Straight lines, and the answer is worse than "we never got around to it": this phone
*already* routes on a downloaded district. `optimizeRoute` picks the on-device road graph
above every other matrix source, so a 🧭 Optimize produces ETAs measured on real roads at
posted speed limits. Then `applyTodayAnchor` — which runs after **every logged stop**, on
the Drive screen's 3-minute refresh, on Download and at boot — re-timed the whole day
through `estimateTravel`, which was haversine × 1.3 ÷ 50 km/h with no knowledge that a map
existed. The good numbers lasted until the first meter was logged. Every re-anchor was a
downgrade, and the more the crew worked the day, the further the times drifted.

The visible tell was there the whole time and read as noise: `wlTimesEstimated` is cleared
by a pack-carried Optimize and set by the re-anchor, so the `~` in front of `Arrive`
appearing minutes after Optimize *was* the road ETA being thrown away.

**`estimateTravel` is a ladder now**, best measurement first, every rung offline:

1. **the district's road graph** (`roadTravelFromCoords`) — real road distance and real
   road time, the same measurement Optimize makes;
2. **the road metres the last solve saved** (`savedRoadTravelFromCoords`) for a day no
   pack covers — road lengths at a nominal speed, so still an estimate, and only the
   between-stop legs;
3. **crow-flies × detour factor**, unchanged, which needs nothing but the pins and so
   always answers.

Driven headless against the committed `maps/huntsville-meg.pack` with eight fully-routable
stops and otherwise identical data, the day's last arrival read **12:44 crow-flies vs
13:41 on the road graph**: +1 min at the first stop, +57 by the eighth. That shape is the
report — fine in the morning, nonsense after lunch — and it is the optimistic direction,
which is the one that fails late rather than early.

### Three things that are easy to get wrong here

**Coverage is judged on the stops, never on the truck.** The origin is usually the live
GPS fix, and a fix parked at the edge of the district must not veto a day the pack covers
perfectly well. It gets its own row and falls back per pair; it is still handed to
`loadGraph` so the *district chosen* matches the run the crew is driving.

**`loadGraph` is not a pure read.** It calls `setActivePack` when it picks a different
district — right for Optimize, wrong for a background re-anchor that would silently
re-point the crew's map and throw away the decode cache on every tick. It takes
`{switchActive:false}` now, and the ETA path measures without adopting.

**The `~` describes the model, not the caller.** `wlTimesEstimated` was
`if(wrote && !opts.travel) set('1')` — "somebody re-anchored, therefore estimated" — which
stops being true the moment a re-anchor can measure. It is `travel.measured ? '' : '1'`
now, and the two Download handlers that cleared it on the line before an
`applyTodayAnchor` which immediately re-derived it are gone; their comment described a
route the very next line re-timed.

### The two cards are one model again

`routeTravel` re-prices the first pending leg from the live fix, because that is the one
leg the solve never saw — but it did so crow-flies, which left the *Route done ~* clock
and the arrival time measured from the same place in two different ways. It goes through
`roadLegMetres` now, the same graph, falling back only when no pack covers both ends.

### Cost, and why the cache is shaped the way it is

`matrix` is one Dijkstra per stop: **266 ms** for 25 stops on the committed pack, which
Optimize already pays but a re-anchor after every logged stop should not. Between two
Optimizes the pending set only ever **shrinks**, so `stopMatrix` caches the stop×stop
block and serves a subset by index remapping — a day is measured once and stays warm.
Only the truck moves, and `roadgraph.js matrixRow` re-measures that one row in **12 ms**.
It shares `fillRow` with `matrix` rather than copying it, so the two cannot disagree; if
they could, an ETA would depend on whether the cache happened to be warm, which is the
worst kind of field report to receive.
