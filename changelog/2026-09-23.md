# 2026-09-23 — Tap the status pill to see exactly what is being sent

## The status pill opens a sync activity log

`js/activity-log.js` (new), `js/queue.js`, `js/dom.js`, `js/api.js`, `js/pages/capture.js`,
`index.html`, `css/capture.css`, `tests/activity-log.test.mjs` (new),
`tests/queue-policy.test.mjs`, `tests/shell-skew-survivable.test.mjs`, `AGENTS.md`,
`ARCHITECTURE.md`, `USER-GUIDE.md`

The pill said "7 sending…" and there was no way to find out *which* seven. Tapping it only
opened Stuck uploads (when something was parked) or silently retried. Now it opens a
**Sync activity** sheet with three sections:
- **Waiting to send**: the offline queue in send order, each write named ("Stop · WO# 40123 ·
  J# J778 · INSTALLED", "Downtime · Truck Issues 25 min · WO# 40124"), with when it was
  queued and how many tries it has had.
- **Running now**: the pill's live jobs.
- **Recent activity**: about two days of history. It covers every Sheet write with its
  outcome (sent, the server's reply such as a duplicate-J# warning, rejected, stuck,
  discarded) and every pill job (worklist download and sync, the PDF, recent days, address
  lookups).

Tapping any row expands every field that was sent. The token is never shown. When something is
parked, a **Stuck** banner leads into the existing Stuck uploads sheet.

**Built so it can never cost the capture page anything.** Each of these choices looks like
something to tidy up, and each one is load-bearing (AGENTS.md §"The status pill's activity
log"):
- **Not in `sw.js` SHELL, and loaded by a dynamic `import()` with a `.catch`.** Any byte
  change to `sw.js` installs a new worker that re-downloads the whole shell on every phone,
  the same fleet-wide effect as the CACHE bump reverted on
  [2026-08-13](2026-08-13.md). The owner chose to leave `sw.js` alone. A phone that can't load
  the file loses the log and nothing else. A static import that failed would have killed the
  capture module, including Log stop and ⟳ Force update, which is the
  [2026-08-14](2026-08-14.md) outage shape.
- **No new named imports on the critical path.** The queue feed rides the existing
  `setQueueHooks`. The new `dom`/`api` hooks are reached through namespace imports with a
  `typeof` check, so a phone with mismatched cached files loses one feed, not the page.
- **Its own IndexedDB database** (`meterlog-activity`). Adding a store to `meterlog` needs a
  `DB_VERSION` bump, and `idb.js` has no `onblocked`. A v5 connection held by a second tab or
  `planner.html` would have hung `enqueue` itself.

**Kept from flooding.** An early estimate put a normal day at around 200 rows. Two rules keep
it down:
- **One row per queued write, updated in place.** An hour offline changes one row's status
  instead of adding a row per retry.
- **A POST made inside a pill job is folded into that job's row.** The worklist sync after
  every logged stop is one row, not two. Repeats within 2 minutes collapse to ×N.

A write that left the queue with no recorded result reads "Left the queue" rather than being
guessed as Sent.

**Verified.** The unit suite passes (719 tests). The page was also driven headless in Edge at
phone width with every spine request intercepted, so nothing reached the Sheet. **Main
scenario, 23/23:**
- two held writes read "2 sending…", and the sheet lists both by WO#;
- expanding a row shows every field and no token;
- releasing the POSTs flips both rows to Sent while the sheet is open, and the opened row stays
  open;
- four failed sends leave one row reading 4 tries;
- six rejections produce a stuck row whose banner opens Stuck uploads;
- a worklist sync is exactly one job row;
- the history survives a reload.

**Skew:**
- the new JS against the previous `index.html`: every top-level handler is bound, and the pill
  falls back to Stuck uploads (5/5);
- the log file answering 404: the page works, the failure is logged to the console, and the
  pill falls back (6/6).
