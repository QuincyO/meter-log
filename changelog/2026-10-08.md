# 2026-10-08 — Photo work-order bot

## Photograph the handheld's list instead of copying numbers by hand

Work orders arrive on the Honeywell handheld as a scrolling list of six-digit
numbers. Getting them into the worklist meant copying each one, or a copy path
into the hold-＋ paste box that didn't always work. Now the installer sends photos of the
list to a Telegram bot running on the owner's PC (`tools/wo-bot/bot.mjs`). Several
overlapping photos are fine for a long list. The installer checks the reply and taps
**✅ Send**. The next **Worklist ▸ ⇩ Download** on the phone has the orders under
**Needs address**, just like a bulk paste.

The PC reads each photo **twice**, locally and for free: Windows' built-in OCR
(`winocr.ps1`) and the Ollama vision model `qwen2.5vl:7b`. Only numbers both readers
report are sent. A number only one reader saw is listed in the reply and left out
until the user types it. On the reference photo both readers got all 15. At
Telegram's compressed size, OCR read `907110` as `007110`, and the agreement rule
held it back instead of queueing a wrong order. Upscaling the image before OCR fixed
the misread. Extraction and the multi-photo merge are pure (`tools/wo-bot/extract.mjs`).

**Spine:** a new `WorklistInbox` tab, the `queueWorklistOrders` write, and
`claimWorklistInbox` inside the `?action=worklist` read. The claim folds an
installer's waiting rows into `Worklist` (pending, after their last `order`) and
stamps `claimedAt`.

**Trap:** the bot must never append to `Worklist` directly. The phone silently
whole-list replaces its `Worklist` slice after every logged stop (`syncWorklist`),
so a direct append is wiped before anyone downloads. The claim runs in the same
request as the read, so no push can land in between. Because it is server-side,
phones on old bytes get the orders too. It locks only after a lockless peek finds
work (the Drive screen polls that read), and a busy lock claims nothing rather than
failing the read. Windows OCR needs `powershell.exe` 5.1; WinRT is missing from
pwsh 7.

**Verification:** `tests/wo-bot-extract.test.mjs` (the reference photo's real OCR
output, the "5160.0 Minute" header, the engine-agreement and photo-merge rules) and
`tests/worklist-inbox.test.mjs`. That one runs the real `Code.gs` queue and claim
against an in-memory sheet: ordering, claim-once, no lock when idle, per-installer,
dedupe. `--dry-run` was also run on the photo at full size, at Telegram size, and as
two overlapping crops (15/15, no duplicates). No phone code, no `sw.js` change, no
`setupSheets()` rerun needed.

**Setup aid:** the bot also logs a refused user's Telegram id, name and username to
its console. That gives the owner the id for `allowedUserIds` without asking for a
screenshot of the bot's reply.

## Switch the bot on and off from Docker Desktop

The bot now runs as the `meter-log-wo-bot` container (`tools/wo-bot/compose.yaml`),
so it no longer depends on a terminal staying open. It shows in Docker Desktop under
`meter-log`, where ■ and ▶ turn it off and on (with `init: true`, a stop takes about a
second), and `restart: unless-stopped` brings it back with Docker Desktop. Its
console, including refused Telegram ids, is the container's **Logs** tab. The image
is only Node plus the OCR tools. The code, `config.local.json` and `state.local.json`
are mounted from the repo, so existing `/link`s carry over and a pull plus a restart
runs new code.

**Trap:** Windows OCR doesn't exist in a Linux container, so inside it Tesseract is the
OCR reader (`ocr.mjs` `ocrRead` picks by platform). Plain Tesseract read **nothing**
from the reference photo, because the digits are small and grey in a busy shot of a
car interior. Fitting the image to 2600 px and applying ImageMagick's local adaptive
threshold (`-lat 60x60-10%`) reads 15/15 at Telegram size and on both overlapping
crops. A smaller offset misread `902580` as `802580` on one crop. The vision model
would have caught that, but the setting is chosen to avoid it. Ollama stays on
Windows, and the container reaches it at `host.docker.internal` (`OLLAMA_URL`).
Only one copy of the bot may poll Telegram, so the `node` and Docker runs must never
overlap (`409 Conflict`).

**Verification:** `--dry-run` inside the container on the reference photo and both
crops: 15 confirmed, 0 unsure, both readers answering. The native `node` dry run still
uses Windows OCR (15/15). There is a new `tests/wo-bot-extract.test.mjs` case that
parses Tesseract's real, noisy output for the reference photo. The live bot was moved
from the terminal to the container (it starts and polls with no conflict), and a
stop/start takes about a second.
