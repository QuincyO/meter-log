# 2026-11-19 — Audits: one installer's work over a period and on a single day

The design is in [the Audits page design](../docs/superpowers/specs/2026-11-19-audits-page-design.md)
and the build order in [the plan](../docs/superpowers/plans/2026-11-19-audits-page.md).

## A read that returns one installer's logs, delays and day times

**The problem:** the audit needs every log an installer has made, every delay they logged and
the start and end time of each of their days. No existing read returns all three: `range`
returns stops and downtime grouped for the phone's day cache with a team header per day, and
the `downtime` read is behind the office password, so the installer's own page could not
call it.

**What shipped:** `GET ?action=audit&installer=<name>` returns
`{ ok, installer, stops, downtime, days }` for that one installer, all dates:

- `stops`: the four printable statuses only (`INSTALLED`, `UTI`, `VISITED`, `UNACCOUNTED`),
  each as `id, timestamp, status, workOrderId, address, lat, lng`. A blank pin is `null`.
- `downtime`: `id, timestamp, category, minutes, workOrderId, note`.
- `days`: `date, departure, returned` from the `Days` tab.

A blank name returns `{ ok:false, error:'installer required' }`.

**Traps worth remembering:**
- **It is token-only on purpose, and must stay out of `ADMIN_GET`.** The installer's own page
  calls it from the phone. This was the owner's decision on 2026-11-18: a named installer's
  logged delays and close-out times are readable with the public token, as their stops
  already are. Drive logs are not, and `driveTracks` stays gated.
- **The `Downtime` rows are not filtered by work mode.** A gap delay is written with a blank
  `workType`, which reads as boat. A mode filter would drop every logged delay from a land
  audit. The browser matches a row to its gap by its note.
- The blank-name refusal is what keeps this from being a crew-wide read. A test pins it.

## The audit's per-day numbers, worked out in the browser

**What shipped:** `js/compute/audit.js`, a pure module with no DOM in it. `prepareAudit(raw,
{ installer, mode })` takes the `audit` read and returns every day in the work mode, oldest
first, each with its logs, its gaps, its pauses and its logged delays. Nothing loads it yet.

The method, as the design states it:

1. Logs are grouped by Toronto calendar day and sorted by time.
2. A gap is the time from one log to the next, with the straight-line distance between the two
   pins. Seven kinds by distance (under 60 m up to over 10 km).
3. The usual time for a kind is the median gap of that kind over **every day in the mode**,
   whatever range is on screen. A kind with fewer than 5 gaps uses the median of every gap.
4. A gap 10 minutes or more over its usual time is a pause. Logged delays whose note names
   that gap (`gap HH:MM–HH:MM`, both clock minutes floored) come off it, never below zero.
   Break, lunch and travel rows are not taken off.
5. An unlogged pause of 45 minutes or more is flagged as a long gap.
6. The day runs from 07:30 (or the first log, when that is earlier) to the time set at
   close-out, 16:00 when the day was never closed out, or the last meter when that is later.

**Traps worth remembering:**
- **Land or boat comes from the date**, through `workTypeOn`, never from a row's `workType`
  tag. `Downtime` rows are not filtered by mode at all.
- **`pct()` is the value at `floor(n × p)` of the sorted list.** It is not the spine's
  `dwellMedian`. The page has to reproduce the report it replaces, which used this definition.
- `workTypeOn` was added to a shell module on 2026-10-14, so this file reaches it through a
  namespace import and a `typeof` check. A phone holding an older copy of
  `installer-lifetime.js` then reads every date as land and still loads.
- The tests use made-up days and the name Pat Example. No real installer's figures may be
  committed: GitHub Pages publishes the whole tree.

## Period statistics, the single day and its two baselines

**What shipped:** three more functions in `js/compute/audit.js`.

- `periodStats(prep, { from, to })` returns everything the period view shows: the headline,
  the average-day bar, the pause figures and histogram bins, the month rows, logged delays by
  category and per day, the output figures, the usual time for each distance kind, and one
  row per day.
- `dayDetail(prep, date)` returns one day with its neighbouring dates and two baselines: the
  up to 30 most recent days of 8 or more orders before it, and every such day.
- `driveStats(legs)` totals a day's drive-log legs: distance, driving time, average and top
  speed.

**Which days each figure counts:**
- Per-day statistics (medians, averages, the bar, the histogram, the month rows) use only days
  with 8 or more orders.
- The day list, the order counts and the category totals use every day in the range.
- Minutes per order in the output block is over every day in the range. The month rows use the
  full days only. Both follow the report this replaces.
- The usual times are not range-dependent. They come from every day in the mode.

**Traps worth remembering:**
- The bar uses averages so its parts add up to the day. "Before the first meter, not logged"
  can be negative on a single day (more delay logged before the first meter than there was
  time). The average is floored at zero for drawing; the per-day value is left as it is.
- A range with no day of 8 or more orders returns `null` for every statistic and `null` for
  the bar. It must never produce `NaN`. A test walks the whole result for it.

## The audit's bar, histogram and timeline as plain HTML

**What shipped:** `js/audit-charts.js`. It returns HTML strings: the stacked average-day bar,
the days-by-pause histogram with the 60-minute allowance marked, the single-day timeline and
the colour key. It also holds the number formats (`fmtClock`, `fmtMin`, `fmtDur`, `fmtDate`).

**Why strings and not a canvas:** the audit has to print cleanly. Boxes with inline widths
print exactly as drawn, need no library, and can be tested in node.

**Traps worth remembering:**
- **The labels are the owner's words.** "Drive to the first order", "Close-out and drive
  home", "Unlogged pauses (breaks included)", "Before the first meter, not logged". The crew
  goes home from the field, so nothing may describe the end of the day as a drive to anywhere
  else. A test pins the four labels and scans for the wrong phrases.
- More delay can be logged before the first meter than there was time before it. The timeline
  scales those two blocks to fit, so the day never draws wider than itself; the tooltip still
  gives the minutes as logged.
- `fmtClock` rounds the whole number of minutes first. Rounding the minutes part alone can
  print "09:60".
- `fmtDate` builds the weekday and month by hand, so it reads the same on every phone.

Files: [js/audit-charts.js](../js/audit-charts.js),

## The Audits office page: one installer's work over a period

**The problem:** the owner had a one-off report made from an export of the sheet: where an
average day goes, how much time between meters is neither work nor a logged delay, and how the
logged delays break down. He wants the same information in the app, for every installer.

**What shipped:** `audits.html`, behind the office password. Pick an installer, Land / Boat /
All, and a date range (all work to date by default). The page shows, in this order:

1. Headline: orders and working days, orders a day, unlogged pause on a typical day, delay
   logged per day.
2. Where an average day goes: one stacked bar from the start of the shift to the end of the day.
3. Unlogged pause time per day: a histogram with the 60-minute break allowance marked, and the
   figures beside it.
4. By month.
5. Logged delays by category, then per day.
6. Output, with the usual time between two logs for each distance.
7. Day by day. Each row is a button that opens that day (the day view is the next change).
8. Method and limits, closed until opened and opened for printing.

A note above the audit says how many days the statistics rest on. Boat and All carry a warning
that the pause figures were only checked against land work. Print uses the browser's own
print, with a print stylesheet.

**How it is put together:**
- `js/pages/audits.js` is the page entry: the login gate, the roster for the picker, the
  dropdown.
- `js/audit-view.js` is the shared view: controls, the address bar, one `audit` read per
  installer kept in memory. The installer's own page will use the same file.
- `js/audit-render.js` turns the numbers into HTML strings. It is pure, so node tests what a
  view says.
- State is in the address (`who`, `mode`, `from`, `to`, `day`), so the browser's Back button
  works and a view can be reopened from its link.

**Traps worth remembering:**
- **The drive-log fetch must stay in `js/pages/audits.js`.** `tests/admin-gate.test.mjs` scans
  every other script as capture-side code that must never name a password-gated read, and the
  phone runs the shared view.
- **The audit files are not in the service worker's `SHELL` list and `sw.js` was not touched.**
  Any byte change to `sw.js` makes every phone re-download the whole shell. The audit needs a
  connection anyway. A test fails if `sw.js` ever mentions them.
- A spine from before the `audit` read answers an unknown action with a bare `{ ok: true }`.
  The view treats an answer with no `stops` list as a failure, not as an installer with no
  logs.
- A closed `<details>` prints empty in Chromium whatever the stylesheet says. The view opens
  method and limits on `beforeprint` and closes it again on `afterprint`.
- Every element is looked up once and tested before use, so a page running new script against
  older cached markup loses one control, not the whole page. A test scans for a bare
  `$('id').` access.

**Checked by driving it:** headless Edge with every request off this machine answered by a
stub (made-up data for "Pat Example"), at 1280 px and 390 px. All sections render, the bar's
seven segments total the bar, a range or mode change makes no second `audit` request, Boat
shows its warning and the empty state, and the page makes GET requests only.
