# 2026-11-19 — Audits: one installer's work over a period and on a single day

The design is in [the Audits page design](../docs/superpowers/specs/2026-11-19-audits-page-design.md)
and the build order in [the plan](../docs/superpowers/plans/2026-11-19-audits-page.md).

## A read that returns one installer's logs, delays and day times

**The problem:** the audit needs every log an installer has made, every delay they logged and
the start and end time of each of their days. No existing read returns all three: `range`
returns stops and downtime grouped for the phone's day cache with a team header per day, and
the `downtime` read is behind the office password, so the installer's own page could not
call it.

**What shipped:** `GET ?action=audit&installer=<name>` returns
`{ ok, installer, stops, downtime, days }` for that one installer, all dates:

- `stops`: the four printable statuses only (`INSTALLED`, `UTI`, `VISITED`, `UNACCOUNTED`),
  each as `id, timestamp, status, workOrderId, address, lat, lng`. A blank pin is `null`.
- `downtime`: `id, timestamp, category, minutes, workOrderId, note`.
- `days`: `date, departure, returned` from the `Days` tab.

A blank name returns `{ ok:false, error:'installer required' }`.

**Traps worth remembering:**
- **It is token-only on purpose, and must stay out of `ADMIN_GET`.** The installer's own page
  calls it from the phone. This was the owner's decision on 2026-11-18: a named installer's
  logged delays and close-out times are readable with the public token, as their stops
  already are. Drive logs are not, and `driveTracks` stays gated.
- **The `Downtime` rows are not filtered by work mode.** A gap delay is written with a blank
  `workType`, which reads as boat. A mode filter would drop every logged delay from a land
  audit. The browser matches a row to its gap by its note.
- The blank-name refusal is what keeps this from being a crew-wide read. A test pins it.

## The audit's per-day numbers, worked out in the browser

**What shipped:** `js/compute/audit.js`, a pure module with no DOM in it. `prepareAudit(raw,
{ installer, mode })` takes the `audit` read and returns every day in the work mode, oldest
first, each with its logs, its gaps, its pauses and its logged delays. Nothing loads it yet.

The method, as the design states it:

1. Logs are grouped by Toronto calendar day and sorted by time.
2. A gap is the time from one log to the next, with the straight-line distance between the two
   pins. Seven kinds by distance (under 60 m up to over 10 km).
3. The usual time for a kind is the median gap of that kind over **every day in the mode**,
   whatever range is on screen. A kind with fewer than 5 gaps uses the median of every gap.
4. A gap 10 minutes or more over its usual time is a pause. Logged delays whose note names
   that gap (`gap HH:MM–HH:MM`, both clock minutes floored) come off it, never below zero.
   Break, lunch and travel rows are not taken off.
5. An unlogged pause of 45 minutes or more is flagged as a long gap.
6. The day runs from 07:30 (or the first log, when that is earlier) to the time set at
   close-out, 16:00 when the day was never closed out, or the last meter when that is later.

**Traps worth remembering:**
- **Land or boat comes from the date**, through `workTypeOn`, never from a row's `workType`
  tag. `Downtime` rows are not filtered by mode at all.
- **`pct()` is the value at `floor(n × p)` of the sorted list.** It is not the spine's
  `dwellMedian`. The page has to reproduce the report it replaces, which used this definition.
- `workTypeOn` was added to a shell module on 2026-10-14, so this file reaches it through a
  namespace import and a `typeof` check. A phone holding an older copy of
  `installer-lifetime.js` then reads every date as land and still loads.
- The tests use made-up days and the name Pat Example. No real installer's figures may be
  committed: GitHub Pages publishes the whole tree.

## Period statistics, the single day and its two baselines

**What shipped:** three more functions in `js/compute/audit.js`.

- `periodStats(prep, { from, to })` returns everything the period view shows: the headline,
  the average-day bar, the pause figures and histogram bins, the month rows, logged delays by
  category and per day, the output figures, the usual time for each distance kind, and one
  row per day.
- `dayDetail(prep, date)` returns one day with its neighbouring dates and two baselines: the
  up to 30 most recent days of 8 or more orders before it, and every such day.
- `driveStats(legs)` totals a day's drive-log legs: distance, driving time, average and top
  speed.

**Which days each figure counts:**
- Per-day statistics (medians, averages, the bar, the histogram, the month rows) use only days
  with 8 or more orders.
- The day list, the order counts and the category totals use every day in the range.
- Minutes per order in the output block is over every day in the range. The month rows use the
  full days only. Both follow the report this replaces.
- The usual times are not range-dependent. They come from every day in the mode.

**Traps worth remembering:**
- The bar uses averages so its parts add up to the day. "Before the first meter, not logged"
  can be negative on a single day (more delay logged before the first meter than there was
  time). The average is floored at zero for drawing; the per-day value is left as it is.
- A range with no day of 8 or more orders returns `null` for every statistic and `null` for
  the bar. It must never produce `NaN`. A test walks the whole result for it.

## The audit's bar, histogram and timeline as plain HTML

**What shipped:** `js/audit-charts.js`. It returns HTML strings: the stacked average-day bar,
the days-by-pause histogram with the 60-minute allowance marked, the single-day timeline and
the colour key. It also holds the number formats (`fmtClock`, `fmtMin`, `fmtDur`, `fmtDate`).

**Why strings and not a canvas:** the audit has to print cleanly. Boxes with inline widths
print exactly as drawn, need no library, and can be tested in node.

**Traps worth remembering:**
- **The labels are the owner's words.** "Drive to the first order", "Close-out and drive
  home", "Unlogged pauses (breaks included)", "Before the first meter, not logged". The crew
  goes home from the field, so nothing may describe the end of the day as a drive to anywhere
  else. A test pins the four labels and scans for the wrong phrases.
- More delay can be logged before the first meter than there was time before it. The timeline
  scales those two blocks to fit, so the day never draws wider than itself; the tooltip still
  gives the minutes as logged.
- `fmtClock` rounds the whole number of minutes first. Rounding the minutes part alone can
  print "09:60".
- `fmtDate` builds the weekday and month by hand, so it reads the same on every phone.

## The Audits office page: one installer's work over a period

**The problem:** the owner had a one-off report made from an export of the sheet: where an
average day goes, how much time between meters is neither work nor a logged delay, and how the
logged delays break down. He wants the same information in the app, for every installer.

**What shipped:** `audits.html`, behind the office password. Pick an installer, Land / Boat /
All, and a date range (all work to date by default). The page shows, in this order:

1. Headline: orders and working days, orders a day, unlogged pause on a typical day, delay
   logged per day.
2. Where an average day goes: one stacked bar from the start of the shift to the end of the day.
3. Unlogged pause time per day: a histogram with the 60-minute break allowance marked, and the
   figures beside it.
4. By month.
5. Logged delays by category, then per day.
6. Output, with the usual time between two logs for each distance.
7. Day by day. Each row is a button that opens that day (the day view is the next change).
8. Method and limits, closed until opened and opened for printing.

A note above the audit says how many days the statistics rest on. Boat and All carry a warning
that the pause figures were only checked against land work. Print uses the browser's own
print, with a print stylesheet.

**How it is put together:**
- `js/pages/audits.js` is the page entry: the login gate, the roster for the picker, the
  dropdown.
- `js/audit-view.js` is the shared view: controls, the address bar, one `audit` read per
  installer kept in memory. The installer's own page will use the same file.
- `js/audit-render.js` turns the numbers into HTML strings. It is pure, so node tests what a
  view says.
- State is in the address (`who`, `mode`, `from`, `to`, `day`), so the browser's Back button
  works and a view can be reopened from its link.

**Traps worth remembering:**
- **The drive-log fetch must stay in `js/pages/audits.js`.** `tests/admin-gate.test.mjs` scans
  every other script as capture-side code that must never name a password-gated read, and the
  phone runs the shared view.
- **The audit files are not in the service worker's `SHELL` list and `sw.js` was not touched.**
  Any byte change to `sw.js` makes every phone re-download the whole shell. The audit needs a
  connection anyway. A test fails if `sw.js` ever mentions them.
- A spine from before the `audit` read answers an unknown action with a bare `{ ok: true }`.
  The view treats an answer with no `stops` list as a failure, not as an installer with no
  logs.
- A closed `<details>` prints empty in Chromium whatever the stylesheet says. The view opens
  method and limits on `beforeprint` and closes it again on `afterprint`.
- Every element is looked up once and tested before use, so a page running new script against
  older cached markup loses one control, not the whole page. A test scans for a bare
  `$('id').` access.

**Checked by driving it:** headless Edge with every request off this machine answered by a
stub (made-up data for "Pat Example"), at 1280 px and 390 px. All sections render, the bar's
seven segments total the bar, a range or mode change makes no second `audit` request, Boat
shows its warning and the empty state, and the page makes GET requests only.

## The audit of a single day: timeline, comparison, delays and the route worked

**What shipped:** the day view. Open it from a row of the day-by-day table or from "Open a
day". In this order:

1. **Timeline of the day**, from the start of the shift to the end of the day. Before the
   first meter it is split three ways from that day's own logged delays. Then one block per
   gap between logs: work, and where the gap ran long, the part logged as a delay and the part
   that was not. A long gap is hatched. Picking a block, or a row of the log list, opens that
   gap: the two orders, the straight-line distance, the usual time for that distance, the
   overrun, and what was logged against it.
2. **This day, and how it compares**: the day beside the installer's 30 worked days before it
   and all their work to date. Each column head says how many days it used.
3. **Delays logged this day.** Dispatch before the first meter is labelled "Dispatch (drive to
   the first order)".
4. **Route worked**: the orders as pins numbered in the order they were logged, joined in that
   order. On the office page, when a drive log exists for the day, a "Show drive log" switch
   lays it over the map, with top speed, average speed, distance, driving time and legs. A
   day with none says "No drive log was recorded this day".
5. **Every log, in order**, with the gap before it, the usual time, and how the gap was read.

Notes above the day say when it ran past the set end time, was never closed out (16:00 is
assumed), or is left out of the statistics (under 8 orders). Back, previous and next worked
day are buttons; the browser's Back button works too.

**Traps worth remembering:**
- `js/audit-map.js` is handed the drive legs. It never fetches. The phone loads it too, and
  the drive log is behind the office password. The view draws the drive-log block only inside
  `if(loadDriveLegs)`, and only the office entry passes a loader. Tests pin both.
- The map's container is static markup that the view never rewrites, so the Leaflet map is
  made once and reused from day to day. It is fitted after a short delay because the card is
  hidden while the period view is up.
- A drive leg is cut into separate lines where two fixes are more than 45 seconds apart, the
  same boundary `js/pages/map.js` uses.
- The route line joins pins with straight lines. The page says it is the order worked, not
  the roads driven.
- Print: holding every card together on one page left half-empty pages. Only charts and
  small blocks are kept whole now, and a heading stays with what follows it. The office
  gate's floating Log out button is hidden in print.
- A failed drive-log read says "Could not load the drive log" and leaves the rest of the day
  on screen.

**Checked by driving it** in headless Edge with a stubbed spine and a made-up drive leg:
opening a day from the table, the hatched block and its detail, the comparison day counts,
pins in logged order, the overlay on and off, the speeds line, Back and previous and next, a
one-log day, a date with no logs, a failed drive-log read, 390 px wide, and both views
printed to PDF (6 and 3 pages) and read.

## How the audit was checked, and what to remember about it

**Checked against the report it replaces.** The 2026-11-18 export of the sheet was fed through
`js/compute/audit.js` and compared with the numbers behind the one-off report, over the same
period: order and day counts, the usual time for all seven distances, orders a day, first and
last meter, the pause figures and every histogram bin, logged delay per day, every month row,
every category, and every day row. All 146 figures matched, with no differences. The check is
a script kept outside the repo, with the export and the report's numbers beside it. None of

the whole tree.

**What differs from that report, on purpose:**
- The end of the day is the time set at close-out (`Days.returned`), 16:00 only when the day
  was never closed out, and the last meter when that is later. The report used 16:00 for
  every day. Only the last block of the average-day bar is affected.
- The report dropped rows tagged `boat` on land dates. The page reads the date only. In the
  checked export no row was in that position, so the totals are identical.
- A distance with fewer than 5 gaps uses the median of every gap. Every distance in the
  checked export had more.

**The traps, in one place** (each is also in `AGENTS.md` §"The Audits pages"):
- Gap delays are written to `Downtime` with a blank `workType`, which reads as boat. Filter
  the stops by mode, never the delays.
- `tests/admin-gate.test.mjs` scans every script except the office page entries as
  capture-side. The drive-log fetch therefore lives in `js/pages/audits.js` only.
- `sw.js` was left alone. The audit files are not in `SHELL` and `CACHE` was not bumped. The
  new menu entry on the log page reaches phones when the installer presses Settings ▸ ⟳ Force

- `audit` is token-only for a named installer and refuses a blank name. That was the owner's

## Fixes from the review of the whole change, before it shipped

A fresh reviewer read the whole change before the push. It found no fault in the numbers, the
spine read, the escaping or the handling of old cached files. These were fixed first:

- **A failed read could leave the previous installer's day on screen.** Open a day for one
  installer, go back, pick another whose read fails, then open a day: the first installer's
  timeline and log list stayed up under "Could not load the audit for" the second, with the
  picker hidden. `render()` un-hid the day view whenever a day was in the address, and its
  two early exits (no installer, failed read) cleared only the period view. Both now clear
  everything drawn for the installer before, hide the day view and bring the period controls
  back so the picker stays reachable.
- **Opening a day now starts at the top of the page.** The day table is the last card of a
  long page, and the content was swapped in place, so the day view opened near its bottom.
  The browser's Back and Forward are left alone: the browser restores its own place.
- **A gap's detail always says what was logged against it.** It showed that line only for a
  gap read as a pause, so a delay logged against a gap read as work was missing from the
  detail (it was in the day's delays table).
- **"Long gap" is now described as what the page flags:** a gap whose *unlogged pause* is 45
  minutes or more, meaning the time over the usual for that stop, less any delay logged
  against it. The page and the guide said "45 minutes or more with nothing logged against
  it", which reads as the length of the gap. A 50-minute gap next door is not a long gap.
- **A clock mark near either end of a bar hangs inward.** The "first meter" and "last meter"
  labels were centred on their marks, so on a day worked past its end time half of the last
  label hung off the card.
- `AGENTS.md` named the wrong file as the one that reaches `workTypeOn` through a namespace
  import. It is `js/compute/audit.js`.

**New tests.** `tests/audit-view.test.mjs` drives the shared view against a small fake DOM
with `fetch` stubbed. The view's mistakes are about order (an answer that arrives late, a
read that fails after another installer was on screen), and until now it had only source
scans. Also pinned: the phone's own lead-gap note (`gap 09:05–09:05` on a first log at
09:05:40) counts as the drive to the first order, and order numbers, addresses and
categories are escaped wherever a day prints them.

**Trap worth remembering:** in a view that swaps what is on screen by hiding and showing,
every exit that shows nothing must clear what was there. An early `return` that clears one
panel leaves the others showing the last thing drawn, under whatever heading came next.

## Download PDF replaces Print on the Audits pages

**The problem:** the Print button opened the browser's print dialog, and getting a file out
of it meant choosing "Save as PDF" there. On a phone that is several taps and looks
different on every device. The owner asked for the PDF itself.

**What shipped:** the button on both pages, for the period and for an open day, is now
**Download PDF**. It builds the file on the device with the vendored jsPDF (the library the
daily-log PDF already uses) and saves it as `Audit - <name> - <dates>.pdf`. Nothing is
sent anywhere and no signal is needed once the audit is on screen. Everything on screen is
in the file, in the same order, as a Letter-size document: text and tables as text, the
charts as shapes, and Method and limits always included.

**The route map has no street background in the PDF.** This was the owner's choice. The
page's street tiles are images fetched from another site; embedding them is fragile and
needs signal. The PDF draws the numbered pins and the route line from the coordinates on a
plain box. On the office page the drive log is drawn too when "Show drive log" is on.

**How it is built, and the rule that follows from it:**
- `js/audit-render.js` now describes each view **once**, as a list of sections made of
  plain blocks (tiles, a table, a caption, a chart). `sectionsHtml()` writes that list as the
  page; `js/audit-pdf.js` writes the same list as the document. Before this the module
  returned HTML strings directly.
- So the page and the PDF cannot differ in a word or a number. **To change what the audit
  says, change the section builders, never a writer.** The audit's wording is the owner's
  and a second hand-written copy of it would drift.

**Traps worth remembering:**
- jsPDF's built-in fonts draw Latin text and a little punctuation, nothing else. Every
  string goes through `pdfText()`, which keeps what the font has (the dashes, the middle
  dot, accents) and drops or replaces the rest. An order number or address from the sheet
  can hold anything.
- A table can run past a page. Its heading row is drawn again on each page it reaches.
- The two buttons kept their ids (`auPrint`, `auPrintDay`). A page whose markup and script
  are out of step still has a working button: old script prints, new script downloads.
- The print stylesheet stays. The browser's own print still gives a clean page.
- `sw.js` was not touched. jsPDF was already in the shell for the daily log, and
  `js/audit-pdf.js` stays out of it like the other audit files.
- A test fails if `js/audit-pdf.js` ever contains `addImage`, so street tiles cannot creep in
  unnoticed.

**Checked:** the PDFs were built from made-up data and read page by page (4 pages for a
period of 48 days, 3 for a day). In headless Edge with a stubbed spine, the button on both
pages saved both files, with no print dialog, no script error and no request made by
building the PDF.

## Send PDF on the Audits pages

**The problem:** the owner wants to send a day's audit to his supervisor as an overview of
how the day went. With Download PDF alone that meant saving the file, opening a message,
and finding the file again to attach it.

**What shipped:** a **Send PDF** button beside each Download PDF, on both pages, for the
period and for an open day. It builds the same file and opens the phone's share sheet with
it attached, so it can go by text, email or any app on the phone. The person picks the app
and the recipient there.

**What it does not do, on purpose:** the page sends nothing itself. There is no supervisor
address stored in the app, no mail from the spine and no upload. The file leaves the phone
only through the app the person chooses.

**Traps worth remembering:**
- **A share sheet opens only as the direct result of a tap.** Building the first PDF means
  loading the library, and on some phones that outlasts what the browser counts as
  "direct", so the share is refused (`NotAllowedError`). The built file is therefore kept.
  The page says "Ready. Tap Send PDF again" and the second tap shares the kept file at once.
  Refused even then, the file is saved as a download and the toast says so.
- **The kept file is tied to the exact view** it was built from (the period or day on
  screen, the drive legs, the "Show drive log" box). A different day is always rebuilt.
- **The file is shared alone, with no title or text.** Beside a file, some apps drop the
  file and others attach the text as a second item.
- **Closing the share sheet is not an error** (`AbortError`): no toast. Success shows no
  toast either, because the browser cannot know the message was sent.
