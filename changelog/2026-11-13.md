# 2026-11-13 — The photo bot takes reassigned orders off the worklist

## Orders that left the handheld can be removed from Telegram

**The problem:** work orders are reassigned and added on the handheld through the day.
The bot only ever added. A ✅ Send queued the numbers that were new and skipped the ones
already on the worklist, so an order taken off the handheld stayed on the worklist until
someone deleted it by hand on the phone.

**What shipped:** a ✅ Send of photos now also asks the Sheet which pending orders were
not in them. The bot lists those orders by number, address and appointment, with a
**🗑 Remove** button. Nothing is removed until it is tapped.

- `/keep 902732` holds an order back from the removal first.
- `/undo` puts the last removal back, with its address, map pin and appointment.
- Removed orders leave the phone on its next **⇩ Download**. No phone update is needed.
- If half the list or more is missing, the message leads with a warning that a photo
  was probably missed.
- A batch of typed numbers only is never compared, and an order logged between the
  list and the tap is left alone.

**How it works:** `queueWorklistOrders` takes `compare: true` and returns `missing` and
`pendingCount`. The new `removeWorklistOrders` action writes each order to a new
`WorklistRemoved` tab and then deletes it from `Worklist`; an order still waiting in
`WorklistInbox` is cancelled instead. When a removed work-order number is queued again,
`claimWorklistInbox` builds the new row from the archived details. `/undo` is that same
re-queue. The nightly `clearDoneWorklistJob` drops archive rows older than 30 days.

**The trap worth remembering:** a plain delete does not work here. The phone replaces
its whole `Worklist` slice after every logged stop, so any phone that has not
downloaded pushes the order straight back, and the crew runs two phones. So each
`WorklistRemoved` row is also a tombstone, and `saveWorklist` drops any incoming order
whose row id is listed there. Three details follow from that:

- The tombstone is the **row id**, not the work-order number. A restored or re-typed
  order gets a fresh id, so it is never caught by an old removal.
- A restore goes through the inbox, like any add. A row appended straight into
  `Worklist` is wiped by the next log.
- The 🗑 button carries a token. A button from an earlier send, or from before the bot
  restarted, answers "out of date" instead of removing against an old list.

**Verified:** the new tests failed before the change and pass after; the full suite
passes. The spine paths are run against the real `Code.gs` over an in-memory sheet:
compare, remove, a stale phone's push, restore, inbox cancel and the sweep. The real
`bot.mjs` was also run through a scripted conversation (photo, ✅ Send, `/keep`, 🗑, a
stale push, the old button again, `/undo`, a typed-only send) against the real `doPost`
and `doGet`, with Telegram, Ollama and the Sheet faked. Nothing was sent to the live
bot or the production Sheet, so the first real removal is the owner's to try.

## The bot no longer re-adds an order you already finished today

**The report:** on the first real use of the removal above, the ⇩ Download afterwards
showed **🔍 Check for duplicate orders (1)**. Order 984647 had been logged as a UTI at
09:32, and the list was photographed again at about 09:48.

**The cause:** the handheld keeps listing an order after it is logged, and a UTI stays
on it. `queueWorklistOrders` skipped a number only if it was still **pending** on the
worklist. A done number was let through on purpose, so a UTI could be re-added for a
revisit. That was harmless while photos were sent once, in the morning. Sending the
whole list again mid-day, which the removal feature asks for, queued every order already
finished that day as a new pending copy.

**What shipped:** the queue now skips a number that is on the worklist in any state,
done included. `claimWorklistInbox` applies the same rule, for an order finished between
the queue and the Download.

**Worth remembering:**
- This is stricter than the phone's own **＋ Add order** and paste box, which still let
  a done number back in. A person typing a number means it; a photo of the whole list
  does not.
- Done rows are swept every night, so a UTI still on the handheld is queued again the
  next morning. A same-day revisit is added by hand on the phone.
- The phone's duplicate check keeps the finished copy and deletes the pending one, so
  nothing logged was lost in the report.

## A note and downtime go on the work order in one place

**The problem:** putting a note and downtime on one order took two screens. The note was
at the bottom of the Edit form in Today's orders; the downtime could only be added from
the same order's card in End of day.

**What shipped:** the work-order card now has a **Note** and a **Downtime** section in
both screens.

- **Today's orders:** tap a row and both are open on the card, with no Edit tap.
- **End of day:** each card has a **▸ Note** row and a **▸ Downtime · travel in** row.
- It is one note and one list. Whatever is added in either screen shows in the other.
- Both save by themselves. Downtime added from Today's orders is sent to the Sheet a
  couple of seconds after the last change, instead of waiting for Finish day.
- Downtime logged earlier with the main **Add downtime** button shows under the list,
  read-only, so it is not entered twice.
- There is one note per work order. A comment on each downtime line was considered and
  dropped at the owner's request.

**Three bugs found on the way, fixed in the same change:**

- End of day replaced its downtime with whatever the Sheet sent back when it opened. An
  entry the Sheet did not have yet disappeared, and the next save then deleted it.
- A confirmed save cleared the phone's unsent copy even when a newer edit was still
  waiting behind it.
- A note typed after the PDF had been prepared in the background was left off the PDF.

**Worth remembering:**

- The two screens share one copy of the downtime state. A slow answer for the screen
  that was just closed is now ignored, or it would replace that state under the open one.
- Today's orders never saves the Departure / Returned times. Those boxes belong to End
  of day and hold defaults while it is closed.
- Removing or resetting a stop still drops the downtime saved on the *next* stop, because
  its gap window changes. That was already true in End of day and is easier to reach now.
- No phone update is forced. Phones get this from Settings ▸ ⟳ Force update.

**Verified:** the suite passes (900 tests, 17 of them new). The real page was driven in
headless Edge with every request to the spine answered by a stub, in land mode: note and
20 min added in Today's orders, seen and changed to 25 in End of day, seen again in
Today's orders; typing kept through a 4-second-late server answer; entries deleted with
no signal stayed deleted and were sent on reconnect; an offline draft PDF carried the note
and the unsent minutes. Boat mode was checked for the first-stop case. Nothing was written
to the production Sheet, and no real phone has run it yet.
