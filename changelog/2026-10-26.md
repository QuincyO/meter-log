# 2026-10-26 — The photo bot reads with AI only

## Windows OCR dropped from the work-order bot

A three-photo batch (30 orders) came back "27 ready". Four numbers were held out as
"only one reader saw these": `106276`, `907955`, `906276`, `906362`. The photos were
clear. Running both readers on copies shrunk to Telegram's ~1280 px reproduced it.
Windows OCR was the reader that failed: it read `07955`, `106276` and `)06362`, and the
vision model read every number right.

The cause is the shape of the photo. Telegram fits a photo to ~1280 px on its long side.
A tall, cropped list photo (1388×7648) arrives about 232 px wide, with digits roughly
10 px tall. `winocr.ps1` upscales before reading, but that cannot restore detail that is
already gone, so OCR lost the leading 9. The agreement rule then did what it was built
to do: it held back every number OCR got wrong. One of those (`106276`) was not a real
order. The rule itself worked, but the slower reader was failing on good photos, and the
user had to retype good orders.

**What shipped:** the owner asked for the AI reader alone.

- `ocr.mjs` calls only Ollama.
- `readPhoto` returns the model's numbers. It throws when Ollama doesn't answer, so the
  reply says so instead of reporting an empty photo.
- `extract.mjs` loses `mergeEngines` and the batch's `unsure` list.
- The bot's replies drop the "not included" warning, and `/help` tells the user to check
  the list against the screen.
- `winocr.ps1` is deleted.

**The trap:** the check on a misread is now the user reading the list before ✅ Send.
A vision model can invent a plausible six-digit number, and nothing cross-checks it any
more. AGENTS.md records why OCR should not be put back beside the model as it was:
Telegram's downscale is what breaks it.

**Verification:** `node --test "tests/*.test.mjs"` passes (763). `bot.mjs --dry-run` on
the three photos at Telegram size read 14 + 15 + 1 = 30 numbers. All 30 match the
screens, including the three that were held back before.

## Optimize with fewer than two orders on the map no longer crashes

The first batch from the photo bot was 30 orders, and 29 of them had no address yet: that
is what the bot always produces, since it only knows the numbers. Tapping Optimize toasted
`Cannot read properties of undefined (reading 'orderedIds')`.

`optimizeRoute` returns `variants: { road:null, straight:null }` when fewer than two orders
can be placed on the map ("nothing to reorder"). Both Optimize handlers — the phone's
`optimizeRouteHandler` in `js/worklist.js` and the desktop planner's in
`js/pages/planner.js` — skip null variants while scheduling, then read
`computed[primaryVariant].orderedIds` from an empty object. The only guard ran before
geocoding (`pending.length < 2`), and it counts orders, not orders with a location.
That bug predates the bot: a bulk paste of address-less orders hits it the same way.

**What shipped:** `unroutableReason(base, pendingCount)` in `js/route.js` returns
"Only N of M orders can be put on the map — fill in the missing addresses, then optimize
again" when neither variant exists, else null. Both handlers check it straight after the
existing constrained-order check, before anything is written, so the stored route is left
as it was.

**Verification:** two new tests in `tests/route.test.mjs` run the real `optimizeRoute` with
one located order and two address-less ones; the first failed before the fix (no export)
and both pass now, with the whole suite (765). `index.html` and `planner.html` load in
headless Edge with every outside host blocked: the changed modules link and no uncaught
exceptions are thrown.
