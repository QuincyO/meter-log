# 2026-11-20 — Optimize writes the found town onto the address; coordinates can be typed as an address; End of day gets a card for downtime before the first order and after the last

## The town a lookup found is written onto the order

**The problem:** Optimize found the pin for an order typed as `123 Main St` and kept
nothing else, so the address stayed `123 Main St`. Two things went wrong from there.
Google Maps by address had to guess the town. And when the order had been through a
**pick a town** chip, the chip wrote the offline map's town onto it, which is the
municipality ("Southwest Middlesex"), while the Log screen's Refresh asks Google, which
names the community ("Glencoe"). The **Keep planned / Use GPS** box compared the two
whole strings, so on 2026-11-19 it asked at every such stop with the house number and
street both right.

**What shipped:**

- A moment after every Optimize, each routable order's pin is looked up and the address
  becomes `typed number + found street, found town`. A toast says how many changed.
- The town is Google's, from the same keyless lookup in the Apps Script that Refresh
  uses, asked about the order's own pin. It is cached per spot, so a pin is asked about
  once. With no signal the town comes from the label the geocoder gave when it found
  the pin, and a later Optimize with signal replaces it.
- The Log screen box asks only when the house number or the street differs.

**Traps worth remembering:**

- The pass writes the address text and nothing else. It never moves a pin, and it must
  not go through the save functions, whose "address changed" rule would blank the pin.
- The typed house number is kept. A pin placed on an estimate reverse-geocodes to the
  neighbour's number.
- The street has to match, and `King St W` against `King St` does not. A lookup that
  lands on the next road changes nothing.
- It runs in the background and stops asking after two unanswered lookups with signal
  showing, so thin signal never holds the Optimize button.
- It does not upload the list. The owner ruled that an Optimize never pushes to the
  sheet, so the new text goes up with the next log or ⇪ Upload. Until then the Drive
  screen's background refresh can put the sheet's older text back, and the next
  Optimize rewrites it.

## Coordinates typed as an address, and a unit with no house number

**The problem:** some orders have no address. A set of railway lights at the side of a
road cannot be found by any geocoder, and there was no way to give an order a position.

**What shipped:** paste `42.933446,-81.486452` into **Street** and type
`-Railway Lights` in **No. / unit**. No new fields.

- The order is pinned at that position as soon as it is saved. No geocoder is asked,
  so it works on a tap with no signal, on the hold, in the planner and for pasted
  lists.
- `-Railway Lights` is a unit with no house number. It shows back as `-Railway Lights`
  when the order is edited, and a lone `-` clears it.
- After the next Optimize with signal the nearest address is written over the
  coordinates, so the paperwork has an address.
- **Navigate always goes to the typed position**, even with "Navigate by address"
  switched on. The address on such an order is only the nearest house.

**The trap:** once the nearest address is written, the address text is no longer where
the order is. A new last column on `Worklist`, `exactPin`, marks these orders so the
phone never re-geocodes them and never navigates by their address. `ensureTab` adds the
header on the next upload. A phone still on older code uploads the column blank, and
the order then follows the Navigate switch like any other.

## Downtime before the first order and after the last

**The problem:** on a land day the only place to enter the morning's delay was the
first order's own Downtime row. It was saved with that order's WO#, so the daily log
printed it on that order's row, which was not true. And a delay that really happened
at the first order could not be told apart from the morning.

**What shipped:**

- End of day has a **Before first order** card at the top of the list and an **After
  last order** card at the bottom, each with the same minutes + reason rows.
- Their minutes are saved with no WO#. The PDF counts them in the delay totals and
  lists them under "Not tied to a WO#".
- The first order's own Downtime row now means that order only.
- The office editor (`edit.html`) shows both cards too.
- Land days only: a boat day has no first-order slot to separate from.

**The audit splits by date (owner's choice).** From 2026-11-21 a delay entered on the
first order counts at that order and is taken off the gap after its log, like any
other order's. On earlier days it still reads as before the first meter, because
that is what it meant then. The two new cards read as before the first meter and
after the last. Method and limits says so.

**Traps worth remembering:**

- The two slots are keyed on a fixed clock, `gap 00:00–00:00` and `gap 23:59–23:59`.
  Keyed on the first or last log's time, one more log would re-key the slot and the
  next save, a whole-day replace, would drop what was in it.
- The phone adds the slots itself when the list it was handed has none. A slot that
  is missing from the list is not hidden, it is deleted by the next save.
- Today's orders shows no card for them but keeps them when it saves.
- A crew member still on older code keeps entering the morning on the first order,
  and from 2026-11-21 the audit reads that as the first order's.

**Checked:** the full suite, and the real End of day screen driven in a headless
browser with the spine answered locally: the cards, the saved entries, the PDF line,
a reopen against a spine that sends the slots itself, and Today's orders.
