# 2026-11-16 — Seven-digit work orders; a tap on Optimize stays offline

## Every photo read "0 read" once the numbers passed 999999

**The problem:** the handheld's work-order numbers went from six digits (902732, …) to
seven (1022668, …). That morning the bot answered 15 photos of the list with
"Photo N: 0 read, 0 new" and an empty batch.

**What was actually happening:** the photos arrived and the vision model read them
correctly. Ollama's log shows about 120 output tokens per photo, which is 15 rows of
seven digits plus a newline. The bot then dropped every number, because `numbersIn`
accepted a run of *exactly* six digits, and a test asserted that seven digits were
rejected. The model prompt also asked for "6-digit" numbers.

**What shipped:** a work order is now six **or** seven digits (`WO_MIN_DIGITS`,
`WO_MAX_DIGITS` in `extract.mjs`). The model prompt and the bot's "I only understand…"
reply both use `WO_DIGITS_TEXT`, so they can't drift from the parser again. Six digits
stay allowed, so older orders and hand-typed numbers still work. Checked by running
`--dry-run` on a photo cropped from the field screenshot: before the fix it read 0
numbers, after it read 14.

**The trap worth remembering:** the reply said "0 read", which looked like a failed
read, but the model had read every row. If the bot reports 0 read, check Ollama's
`server.log` first. Output tokens on `/api/generate` mean the model saw numbers and the
bot rejected them. A failed read shows up as "the AI reader (Ollama) didn't answer".
The spine and the phone never checked work-order length, so only the bot needed the
fix.

## A tap on Optimize no longer looks addresses up online

**The problem:** a tap on 🧭 Optimize used the offline map for the road distances,
but an address the map's address index couldn't find still went to Google, then to
OpenRouteService. A field tap that afternoon ended with "1 parked (fix address) ·
lookups failed: OVER_QUERY_LIMIT — check the Google API key setup". Probing both
services showed both daily geocoding quotas were spent: Google answered
`OVER_QUERY_LIMIT` ("exceeded your daily request quota", the 300/day cap in
DEPLOY.md) and ORS answered 403 "Quota exceeded". The message blamed only the Google
key, and the installer had pressed the button that is meant to be offline.

**What shipped:** a tap is fully offline, by the owner's decision. `optimizeRoute`
takes `offlineGeocode`, and `geocodeOne` takes `offlineOnly`. With either set, the
district's address index is the only geocoder and a miss parks the order. The
Optimize handler passes the press to the home and crew-start pin lookups too. On a
tap the toast says "N not on the offline map (fix address, or hold Optimize to look
up online)". The hold, the desktop planner and the Settings home pin still fall
through to Google and ORS. Old cached files on either side keep the old online
behaviour, and nothing breaks.

**The trap worth remembering:** what spent ~1,300 lookups in one day is not known
yet. A normal Optimize only geocodes orders without a pin, and nothing that touches
geocoding changed recently. The Google Cloud Geocoding metrics for the day would
show whether it was one burst or steady use.
