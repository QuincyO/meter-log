# 2026-08-14 — Outage: Google revoked the script's authorization overnight

`DEPLOY.md` (troubleshooting entry; no code changed)

The crew's phones came up with "cannot connect to the server" this morning — a
**fleet-wide production outage of the spine**, live from sometime between
2026-08-13 ~21:15 (last Sheet write) and ~03:00 Toronto (the nightly
`exportSheetToGithub()` trigger produced no commit). Root cause: **Google had
revoked the script's OAuth grant to execute as its owner.** The web app is
`executeAs: USER_DEPLOYING`, so with the grant gone Google refused every `/exec`
request upstream of `doGet` — HTTP 403 with the Drive *"Access Denied — You need
access"* wall — and the same revocation silently killed the 3am export trigger.
No email announced it (no security alert, no Apps Script failure summary).

The fix was one tap: the owner opened the `/exec` URL in a signed-in browser,
got the re-consent screen, and granted; the very next anonymous request returned
`{ok:true, …}`. Total outage ~15 hours, all of it overnight/morning.

What the diagnosis established, in the order it discriminated:

- **The 403 wall sits in front of our code.** Same page with or without the
  token, any user agent — so `SHARED_TOKEN`, `Code.gs` and the phones were never
  suspects. A Google HTML page at `/exec` means Google-level refusal, full stop.
- **`git` was clean by construction**: `Code.gs`/`appsscript.json` last changed
  2026-08-10 and the app demonstrably worked through the 13th, so no deploy did
  this. The Workspace status dashboard showed no incident; the owner's Drive and
  the Sheet itself were healthy (readable via API, last write 21:15).
- **A redeploy does NOT fix a revoked grant — and its success is itself
  evidence.** The CI workflow was dispatched (`workflow_dispatch`, no commit
  needed); `clasp push` + `clasp deploy -i` succeeded and created version 81
  with the manifest's `ANYONE_ANONYMOUS` — and `/exec` still 403'd. That
  eliminated "the deployment's access flipped" and proved the project existed
  and the owner's *clasp* grant (a separate OAuth client) still worked.
- **The discriminator was the owner opening `/exec` in a signed-in browser.**
  JSON → anonymous-only block; the same wall → Drive ACL; a consent screen →
  revoked authorization. It was the consent screen.

Traps worth remembering:

- **The Drive "You need access" wall at `/exec` can mean a revoked grant, not a
  sharing problem.** Nothing in the console shouts about it, no email arrives,
  and the deployment config reads as perfectly correct the whole time — because
  it is. Send the owner to the `/exec` URL in a signed-in browser *first*; it is
  a 10-second test and when the cause is the grant it is also the fix.
- **The nightly export doubles as a dead-man's switch.** A missing
  `Nightly sheet export — <date>` commit on `main` means the spine's triggers
  were dead overnight — that absence bracketed the outage window before any
  console was opened. Worth checking on any morning report of server trouble.
- **The phones' offline-first design carried the field through.** Capture kept
  queueing to IndexedDB; the standing instruction during any spine outage is
  **do not clear site data / reinstall the PWA** — that destroys the unsent
  queue. Everything drained on its own once the grant was restored.
- Why the grant vanished is **unknown** — no password change, no security
  event, no email. If it recurs, check myaccount.google.com ▸ Security ▸
  Third-party access before anything else, and treat a second occurrence as a
  pattern worth a real dead-man's alarm (the export commit is already the
  signal; something should watch for its absence).

## Navigate by pin or by address — the installer's switch, not the source's

`index.html`, `js/worklist.js`, `js/worklist-tuning.js`, `css/capture.css`,
`tests/worklist-directions.test.mjs`, `tests/worklist-tuning.test.mjs`,
`ARCHITECTURE.md`, `USER-GUIDE.md`

The 🧭 on a worklist card and the Drive screen's **Navigate** share one function
(`openDirections` → `destOf`), and which destination it hands the maps app has now been
answered both ways in the field: address-first until 2026-08-13, pin-first since. Both
arguments are right some days. The pin is the exact coordinate the route was built
around, so the truck and the route map agree by construction; the address lets Maps
geocode it with knowledge our lookup didn't have, which is the better answer on a new
build or a landmark. Which one wins varies **by day and by address**, so it has stopped
being a source edit and become **Route tuning ▸ Navigate by address instead of map pin**
(`localStorage['wlNavBy']`, default `'pin'` — an untouched phone behaves exactly as it
did before). The hint under it says why you'd switch, because a toggle whose two states
look identical from the outside is a toggle nobody flips on purpose.

Four decisions worth the words:

- **It picks a preference, not a rule.** Each mode falls back to the other when the order
  hasn't got it, so Navigate never becomes a button that does nothing. An order with a pin
  and no address still navigates in address mode; an order with an address and no pin still
  navigates in pin mode.
- **The parked carve-out holds in BOTH modes, and it is structural rather than
  conditional.** `geoFail` (📍 fix address) / `geoAmbig` (⚠ pick a town) orders keep a
  last-known pin that `route.js` never blanks, and that pin is precisely the one already
  known to be in the wrong place. The `isParked` gate therefore stays on the line *above*
  the branch: a parked order simply has no pin to prefer, so neither mode can steer by it.
  **Gate it inside one arm and "coordinates mode" quietly starts driving to known-bad
  pins** — pinned by a test asserting the gate precedes the branch, not just that it exists.
- **One toggle for both surfaces**, because it is one function and one act. Two switches
  would be two things to keep straight in a truck.
- **Device-local, saved on tap, and deliberately not routed through `save()`.** It changes
  nothing the office or the router reads, so it sits in the `.tune-local` block below Save
  with *Show driving stats* — and it must not borrow `save()`'s toast, which promises an
  Upload that would not carry it. It gets its own one-word confirmation instead, since the
  effect is invisible until the next Navigate press.

**Where the accessor lives, and why it isn't next to `destOf`.** `navByPin()`/`setNavByPin()`
are exported from `js/worklist-tuning.js` even though the only reader is `worklist.js`,
because `worklist.js` already imports `initWorklistTuning` from there — the reverse import
would be a cycle (the same reason `js/drive.js` never imports `worklist.js` back). One key,
one default, one place, no duplicated literal.

**No `sw.js` CACHE bump**, on the 2026-08-13 reasoning: no new module or stylesheet, only
edits to files already in `SHELL`, so the rollout stays per-phone via Settings ▸
⟳ Force update rather than every phone re-caching the whole shell at once on boat signal.

### Verification

`node --test "tests/*.test.mjs"` — **655/655** green, including the rewritten
`worklist-directions` tests (the old ones asserted a *source order* — `coords < address` —
which no longer means anything now that both destinations are built and the preference
chooses; they assert the fallback shape and the gate-before-branch rule instead).

Then driven end-to-end in headless Edge (`VERIFY.md` §3, every non-localhost request failed
at the browser per §4 so nothing could reach the production Sheet), with `window.open` and
`navigator.clipboard.writeText` stubbed to record their arguments: **19/19**. Five seeded
orders — clean pin+address, `geoFail`+pin, pin with no address, address with no pin,
`geoAmbig`+pin — pressed on the worklist 🧭 and again on the Drive screen's **Navigate**, in
both modes. Pin mode sent the clean order to `45.3311,-79.2117` and everything flagged or
pinless to `<address>, ON`; address mode sent every addressed order to `<address>, ON` and
fell back to `45.5,-79.4` for the one with no address; both modes, both surfaces copied the
card's address line and never a coordinate pair. The toggle wrote its key on tap with no
Save press and survived a reload.

**A harness trap that reads as a bug in the feature.** The first run failed one check —
"the toggle survives a reload" — and the cause was the drive, not the code: a page loaded
straight at `#tuning` **never opens the tuning screen**, so `loadControls()` never runs and
every control reads as its markup default. The discriminator was the *pre-existing*
`tuneShowDriveMetrics`, which was equally unreflected on that path with its key set;
opened the way the crew does (the ☰ nav's `navTuning`), all three controls painted their
stored values. Worth remembering next to the `#hash`-only navigation trap from 2026-08-13:
a screen this app routes to is not necessarily a screen a URL can land on.

**Noticed while verifying, deliberately not fixed here:** `pullVal(store.get('wlCommutePull'))`
returns **0**, not the documented 70, when the key has never been set — `Number(null)` is `0`
and `isFinite(0)` is true, so the `|| 70` intent never fires. That is the commute-pull weight
`worklist.js planShape` feeds the router on any phone whose installer has not opened Route
tuning and pressed Save. Unrelated to this change and untouched by it; flagged rather than
fixed, since it moves real routes.
