# 2026-08-13 — Hold ＋ Add order to paste a whole list of work order numbers

`index.html`, `js/worklist.js`, `js/worklist-dedup.js`, `css/capture.css`, `sw.js`,
`tests/worklist-bulk-add.test.mjs`, `USER-GUIDE.md`, `ARCHITECTURE.md`

Building a worklist meant typing every order through the single-order form, one at a
time — but the way a list actually arrives is as a block of work order numbers from the
office, addresses to be filled in afterwards. The address half of that workflow already
existed (`worklist-address-fill.js` documents "WO#s first, addresses after" in its own
header); the numbers half didn't. Now it does: **hold ＋ Add order for two seconds** and
the `#wlBulkAdd` sheet opens with a textarea — paste the numbers one per line, tap
**Add orders**, and each line becomes a pending order. A tap on the same button opens
the single-order form exactly as before.

Design choices that keep it inside the app's existing shapes:

- **The gesture is the Optimize button's own binder.** `bindOptimizeGesture` was
  already generic tap-vs-hold wiring (`createPressHold` from `js/press-hold.js`); it is
  simply bound a second time. That inherits the load-bearing details for free: pointer
  capture (the sheet opens under a finger that is still down), synthetic-click eating,
  contextmenu suppression, and **no `touchstart` listener ever** — the selection guard
  is a standalone `#wlAddBtn` CSS rule, because the exact `#wlOptimize{` shape is
  pinned by `tests/press-hold.test.mjs` and must not gain a merged selector.
- **Parse + dedupe is pure and lives in `worklist-dedup.js`** (`bulkAddPlan`): lines
  trimmed (CRLF pastes shed their `\r`), blank lines ignored *without* counting as
  skipped, duplicates — of an earlier line or of a non-done order already on the list —
  skipped and reported in the toast ("Added 3 orders · skipped 1 duplicate"). A number
  matching only a **done** order goes through, same as `wlSave`'s guard: the revisit is
  legitimate and the done copy gets swept nightly anyway.
- **Bulk adds take the single-add path into the day.** Every created id goes through
  `addToQueue` → `offerAddTo()` — the documented only way work joins a day already
  under way — so on a locked day a pasted batch raises one "2 orders added" chooser
  instead of smuggling work past the lock.
- **Addressless orders need no new plumbing.** They land in the "Needs address" group,
  light up 📝 Fill in missing addresses, and the existing walkthrough takes it from
  there. No spine change at all: the orders are IndexedDB rows and the ordinary
  Upload/Download sync carries them.

Two traps worth remembering:

- **`press-hold`'s eat-one-click flag assumes the browser's synthetic click.**
  `up()` arms `eatClick` and the click that follows a real pointerup consumes it. A
  headless drive that dispatches an *untrusted* `pointerup` gets no synthetic click, so
  the flag stays armed and silently swallows the **next** programmatic `.click()` —
  which looks exactly like "the tap path is broken" (three failing checks) when nothing
  is wrong. Dispatch a `.click()` after the synthetic `pointerup` to play the browser's
  part.
- **The service-worker CACHE version is pinned in THREE test files, not two:**
  `cache-refresh`, `installer-metrics-cache-docs`, and — easy to miss —
  `drag-autoscroll`. Grep for the literal `meterlog-v` on every bump.

## Directions navigate to the order's pin, not its address

`js/worklist.js`, `tests/worklist-directions.test.mjs`, `ARCHITECTURE.md`, `USER-GUIDE.md`

The 🧭 button on a worklist card and the Drive screen's big **Navigate** button share one
function — `openDirections()` — and it handed the maps app the order's **address text**
(`+ ", ON"`), reaching for the cached pin only when an order had no address at all. It now
goes the other way: **a trusted pin is the destination, and the address is the fallback.**

The problem with the old order is that an address string is not a location — it is a
request for the maps app to geocode it a *second* time, with its own guess and no
knowledge of which townships this crew works in. A rural line lands on the wrong side of a
lake; a road name that repeats in three townships picks one. Meanwhile the pin is the exact
coordinate the route was built around and the one the crew is looking at on the route map,
so the truck and the plan now agree by construction.

The trap worth remembering: **the old precedence was deliberate, not an oversight.** The
code comment and `ARCHITECTURE.md` both argued it — *"the typed address is the source of
truth: a mis-geocoded pin must not steer the truck"* — and that argument is not wrong, it
is just narrower than it looked. What survives of it is the carve-out, and it is
load-bearing: a **parked** order (`geoFail` → 📍 fix address, `geoAmbig` → ⚠ pick a town)
keeps its last-known pin, because `route.js` never blanks one, and that pin is precisely
the one already known to be in the wrong place. So `destOf` gates the coordinates on
`isParked(item)`, not on `coordsOf(item)` alone, and a flagged order still navigates by its
address. Reusing `isParked` rather than writing a fresh geoFail/geoAmbig test is the point:
there is one answer in this repo to "may the truck be routed on this pin", and the navigate
path is now a caller of it instead of a second opinion.

**The clipboard half is untouched.** `addressLabel()` still copies the card's unit +
address line, still synchronously inside the tap handler and still before the iOS scheme
hand-off — the destination string, which may now be a bare `lat,lng`, never reaches the
clipboard (asserted). The three URLs downstream needed no change at all: `daddr=` and
`destination=` take a coordinate pair as happily as a street.

Two things deliberately left alone, so the next agent knows they were seen: the card's 🧭
only renders when `item.address` is set, which is still right because pins come *from*
forward-geocoding the address (a pin with no address is not a state a real order reaches);
and `js/drive.js`'s `driveNav.disabled` gate reads `item.lat && item.lng` by truthiness
rather than through `coordsOf`, which differs only for junk coordinates on an order that
also has no address.

`tests/worklist-directions.test.mjs` pins all three properties — pin before address,
`isParked` in the gate, address-not-coordinates on the clipboard — as source-shape
assertions, since `worklist.js` is DOM-bound and `node --test` cannot import it.

**No `sw.js` CACHE bump — deliberately, and it was briefly bumped and then put back.**
The letter of the rule never required one (no new module or stylesheet, only edits to files
already in `SHELL`), and the argument for bumping anyway was that it saves telling every
phone to press ⟳ Force update. The installer's call went the other way, and the reasoning is
the stronger one: a bump makes **every** phone in the field re-cache the whole shell at once
on its next open, so if anything in the change is wrong, it is wrong on all of them
simultaneously, on boat signal, with no one having asked for it. Without the bump the
rollout is per-phone and on purpose — ⟳ Force update from GitHub when the crew is somewhere
they can afford it. Worth knowing for whoever bumps next: the constant is what the SW keys
its cache on, so **changing it in either direction** (v42 → v43 *or* v43 → v42) is a new
worker and one full `addAll(SHELL)` re-download — a revert costs the same wholesale
re-cache it is reverting, for any phone that already took the bump. Worth knowing for
whoever *doesn't*: not bumping is not a gate. The fetch handler is
stale-while-revalidate, so a phone still picks up the new `worklist.js` on its own within an
open or two whatever `CACHE` says; the bump only decides whether the shell lands **all at
once and immediately** or **file by file and lazily**.

Then driven end-to-end in headless Chromium (`VERIFY.md` §3, every non-localhost request
aborted at the browser so nothing could reach the production Sheet), with `window.open` and
`navigator.clipboard.writeText` stubbed to record their arguments: **8/8** — four seeded
orders (clean pin, `geoFail` + pin, `geoAmbig` + pin, no pin) pressed on the worklist's 🧭
and again on the Drive screen's **Navigate**, both surfaces identical. The clean order
opened `…&destination=45.3311%2C-79.2117`; all three others opened
`…&destination=<address>%2C%20ON`; every one of the eight copied the card's own address
line. Worth knowing for the next drive: a `page.goto` that differs only in the `#hash` is a
**same-document** navigation, so seeding `localStorage`/IndexedDB and then "reloading" into
`#worklist` leaves the un-seeded modules — and the auto-opened settings sheet — in place,
covering the list; add a throwaway query string to force a real load.

**And the trap that cost a full round trip: a commit on a feature branch is not a deploy.**
All of the above was green and pushed, and the crew's phone still drove 35 km south to
*Le Baron Distributors* off `"788 Supersign rd, ON"` — the exact bug, with a correct pin
sitting on the route map two screens away. Nothing was wrong with the change. GitHub Pages
serves the repo root **from `main`**, the commit was on
`claude/navigate-button-gps-coords-4617oc`, and so Settings ▸ ⟳ Force update did its job
perfectly and re-downloaded the *old* bytes. The failure mode is nasty because every signal
says shipped: tests pass, the branch is pushed, the phone has been refreshed, and the bug is
still there — which reads as "the fix doesn't work" rather than "the fix isn't there".
Before concluding a shipped change didn't work, check what `origin/main` actually holds
(`git show origin/main:<file>`); it took one command to settle here. `AGENTS.md`'s standing
rule now says so next to "an unpushed commit is work that has not shipped".

# 2026-08-13 — End of day stops throwing the review away, and the PDF prints what the phone is holding

A field report with three parts, and the first two turned out to be the same afternoon on a
slow spine: *"when I click end of day and click into a work order to add downtime it sort of
kicks me out and I have to press end of day again… and if I scroll down and hit finish day
too quickly none of my downtime gets saved onto the PDF copy — I have to add my downtime and
then wait like 30 seconds before I'm safe to submit."* Plus two asks: default the day's start
and end times, and copy the day's tally to the clipboard when the log is generated.

The installer's own diagnosis was close enough to name the bug: *"what gets populated is
what's on the Google sheets first before what's saved onto the phone locally, so if I submit
before the Google sheet is updated then it shows blank."*

## The end-of-day review is live state, and a late server read was bulldozing it

`js/pages/capture.js`, `css/base.css` (read-only), `tests/eod-review-live.test.mjs` (new)

`loadDay('eod')` paints the review **twice** — instantly from the IndexedDB day cache, then
again when `?action=day` and `?action=idle` land. `apiGet` has no timeout, and at quitting
time the spine is cold and holding a global write lock, so that second paint can arrive ten
seconds after the sheet opened — i.e. while the crew is already typing in it. It calls
`setGapData`, which **replaces `eodGaps` wholesale** (allocations, `_views` and all), and
`renderEod`, which does `innerHTML=''` and rebuilds every card collapsed.

- **That is where "it kicks me out" comes from.** A `.sheet` is a full-viewport,
  **bottom-anchored** backdrop (`css/base.css` `align-items:flex-end`) with the card floating
  on it, so rebuilding the list changes the card's height and resets its scroll — and the tap
  already in flight lands on the dim area, which `closeSheets()` read as a dismiss. Every
  sheet at once, mid-review, no confirmation. Two independent guards now: `eodTouched` (set by
  expanding a card, typing minutes, editing a bookend) makes the second render a no-op, and
  the backdrop dismiss requires the **pointerdown** to have started on the backdrop, so a
  reflow can no longer fake the gesture.
- **It was data loss, not just an annoyance.** `Code.gs saveTravel` **replaces** the day's
  gap-tagged Downtime rows rather than adding to them, so an `eodGaps` emptied by the rebuild
  could be posted straight over deductions already on the Sheet.
- What the freeze costs: for that open, the review keeps the locally-computed gaps instead of
  the spine's merged-boat ones. Display-only — the PDF's travel column is built spine-side at
  Finish — and a re-open with nothing touched renders the authoritative ones again.
- The gap-editor's **category dropdown** now goes through `syncNet` like the minutes box. It
  set `a.category` and nothing else, so a category change never reached the dayCache stash and
  never re-triggered the summary prefetch.

## The PDF netted the downtime out of travel but never printed it

`js/compute/summary.js`, `tests/eod-pending-downtime.test.mjs` (new)

The actual cause of the blank delays, and it is one line of omission.
`buildLocalSummary` threads `pendingTravel` into `computeGapsLocal` so the **Travel** column
is right — and then returns the untouched `downtime` array. Every delay figure on both
templates is built from that array: the land per-WO **DELAYS** grid, the boat "Delay Time"
box, the "Delays:" footer. So a Finish tapped before the 2s-debounced `prefetchEodSummary`
had finished missed the 5s race, fell back to the local builder, and drew a PDF with a blank
delay grid — while the same minutes reached the Sheet a second later via the step-2
`saveTravel`. Wait 30 seconds and the prefetch has landed, the spine's summary (built *after*
its own `saveTravel`) is correct, and everything looks fine. Exactly the reported shape.

It now synthesizes the rows `saveTravel` would have written — same `gap HH:MM–HH:MM` note,
the arriving WO, category, minutes — with two rules that are load-bearing:

- **Drop the existing gap-tagged rows first.** `saveTravel` is a whole-day replace, so a
  partly-synced review that kept the saved copy too would double every re-edited deduction.
- **Gate it on a non-empty pending list**, the same rule `computeGapsLocal` already uses.
  With nothing pending the saved rows *are* the review, and the printed rows and the travel
  netting must always describe one set, or the PDF disagrees with itself.

`collectNotes` already skips `gap …` notes, so the synthesized rows stay out of the Notes
block — pinned by a test, because the note column is overloaded and these rows are the
overload.

**And `await flush()` was never a barrier.** The re-entrancy guard was `if(flushing) return;`,
which resolves *instantly*; since `enqueue` fires an un-awaited `flush()`, the guard is armed
for the whole drain. Every "drain the queue, then read the Sheet" call site —
`previewDailyLog`, the live `endOfDay`, the End-of-day open — was therefore not waiting at
all, and could build a summary from a Sheet still missing rows the phone had just queued.
`flush()` holds the in-flight **promise** now and hands it back. Two things fall out of that:
`drain()` must never reject (the awaiting handlers have no try/catch), and End of day now
opens the sheet *before* draining, or a long queue leaves a dead button and a blank screen.
`eodStateKey` also fingerprints the day's own rows now — without it, a summary prefetched
before a downtime row existed still "matched" at Finish and was reused verbatim.

## Start / End default to 7:30 and 4:00

`js/config.js`, `js/pages/capture.js`, `tests/eod-time-defaults.test.mjs` (new)

New `DAY_START_DEFAULT` / `DAY_END_DEFAULT`, seeded into the two boxes when End of day opens.
`renderDayData`'s existing truthy guard keeps them a *default*: a time already saved for the
day still overwrites them, and either can be typed over. **Deliberately not
`ROUTE_DEPART_TIME` / `ROUTE_DAY_END`** despite the 16:00 coincidence — both are documented as
answering exactly one routing question, and giving either a second job is how the finish-by
dial came back last time. `edit.html` deliberately does **not** prefill: a reprint of a past
day that recorded no times must stay blank rather than gain an invented shift.

## The day's tally lands on the clipboard with every PDF

`js/compute/tally.js`, `js/utiReasons.js`, `js/worklist.js`, `js/pages/capture.js`,
`index.html`, `tests/day-tally-block.test.mjs` (new)

`Dispatched:` / `Installed: n` / `UTI: n` / `TR: n` / `EER: n`, copied by **Finish day**,
**Generate daily log** and a new **📋 Copy tally** button on the End-of-day sheet.

- **`Dispatched` is copied empty.** That number lives in a system this app never sees, so the
  installer types it on paste; a fabricated 0 would read as a real count.
- **`EER` is a subset of `UTI`, not a sibling** — a UTI whose reason is `Electrical Repair`
  is counted on both lines. Subtracting it would make the UTI line disagree with the UTI
  total printed on the PDF beside it. The reason string is exported as
  `utiReasons.js EER_UTI_REASON` and a test asserts it is still *in* the picklist: rename the
  pick without the constant and the EER line silently reads 0 forever.
- **`TR` can only come from the worklist.** An appointment lives on the order
  (`appointmentDate`/`appointmentTime`), never on the logged stop, so a hand-typed work order
  that was never on the list can't be counted, and `edit.html` reprints get no tally at all.
  Counted by date **regardless of `wlStatus`**: an appointment kept but logged as a UTI, and
  one the crew never reached, both still happened that day.
- **The trap: a clipboard write after an `await` is refused on iOS.** Both PDF handlers sit
  behind several awaits (up to the 5s summary race) plus jsPDF's lazy load, so the copy fires
  **synchronously at the top of each handler** — the same rule the plan-mode WO# copy has
  carried since June — and every number it needs is pre-read into `tallyCache` (refreshed on
  load, after each log, and on End-of-day open) rather than fetched at tap time. Because an
  implicit copy can still be refused, the on-demand button is the guaranteed path.
