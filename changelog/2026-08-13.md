# 2026-08-13 — Hold ＋ Add order to paste a whole list of work order numbers

`index.html`, `js/worklist.js`, `js/worklist-dedup.js`, `css/capture.css`, `sw.js`,
`tests/worklist-bulk-add.test.mjs`, `USER-GUIDE.md`, `ARCHITECTURE.md`

Building a worklist meant typing every order through the single-order form, one at a
time — but the way a list actually arrives is as a block of work order numbers from the
office, addresses to be filled in afterwards. The address half of that workflow already
existed (`worklist-address-fill.js` documents "WO#s first, addresses after" in its own
header); the numbers half didn't. Now it does: **hold ＋ Add order for two seconds** and
the `#wlBulkAdd` sheet opens with a textarea — paste the numbers one per line, tap
**Add orders**, and each line becomes a pending order. A tap on the same button opens
the single-order form exactly as before.

Design choices that keep it inside the app's existing shapes:

- **The gesture is the Optimize button's own binder.** `bindOptimizeGesture` was
  already generic tap-vs-hold wiring (`createPressHold` from `js/press-hold.js`); it is
  simply bound a second time. That inherits the load-bearing details for free: pointer
  capture (the sheet opens under a finger that is still down), synthetic-click eating,
  contextmenu suppression, and **no `touchstart` listener ever** — the selection guard
  is a standalone `#wlAddBtn` CSS rule, because the exact `#wlOptimize{` shape is
  pinned by `tests/press-hold.test.mjs` and must not gain a merged selector.
- **Parse + dedupe is pure and lives in `worklist-dedup.js`** (`bulkAddPlan`): lines
  trimmed (CRLF pastes shed their `\r`), blank lines ignored *without* counting as
  skipped, duplicates — of an earlier line or of a non-done order already on the list —
  skipped and reported in the toast ("Added 3 orders · skipped 1 duplicate"). A number
  matching only a **done** order goes through, same as `wlSave`'s guard: the revisit is
  legitimate and the done copy gets swept nightly anyway.
- **Bulk adds take the single-add path into the day.** Every created id goes through
  `addToQueue` → `offerAddTo()` — the documented only way work joins a day already
  under way — so on a locked day a pasted batch raises one "2 orders added" chooser
  instead of smuggling work past the lock.
- **Addressless orders need no new plumbing.** They land in the "Needs address" group,
  light up 📝 Fill in missing addresses, and the existing walkthrough takes it from
  there. No spine change at all: the orders are IndexedDB rows and the ordinary
  Upload/Download sync carries them.

Two traps worth remembering:

- **`press-hold`'s eat-one-click flag assumes the browser's synthetic click.**
  `up()` arms `eatClick` and the click that follows a real pointerup consumes it. A
  headless drive that dispatches an *untrusted* `pointerup` gets no synthetic click, so
  the flag stays armed and silently swallows the **next** programmatic `.click()` —
  which looks exactly like "the tap path is broken" (three failing checks) when nothing
  is wrong. Dispatch a `.click()` after the synthetic `pointerup` to play the browser's
  part.
- **The service-worker CACHE version is pinned in THREE test files, not two:**
  `cache-refresh`, `installer-metrics-cache-docs`, and — easy to miss —
  `drag-autoscroll`. Grep for the literal `meterlog-v` on every bump.

## Directions navigate to the order's pin, not its address

`js/worklist.js`, `tests/worklist-directions.test.mjs`, `ARCHITECTURE.md`, `USER-GUIDE.md`

The 🧭 button on a worklist card and the Drive screen's big **Navigate** button share one
function — `openDirections()` — and it handed the maps app the order's **address text**
(`+ ", ON"`), reaching for the cached pin only when an order had no address at all. It now
goes the other way: **a trusted pin is the destination, and the address is the fallback.**

The problem with the old order is that an address string is not a location — it is a
request for the maps app to geocode it a *second* time, with its own guess and no
knowledge of which townships this crew works in. A rural line lands on the wrong side of a
lake; a road name that repeats in three townships picks one. Meanwhile the pin is the exact
coordinate the route was built around and the one the crew is looking at on the route map,
so the truck and the plan now agree by construction.

The trap worth remembering: **the old precedence was deliberate, not an oversight.** The
code comment and `ARCHITECTURE.md` both argued it — *"the typed address is the source of
truth: a mis-geocoded pin must not steer the truck"* — and that argument is not wrong, it
is just narrower than it looked. What survives of it is the carve-out, and it is
load-bearing: a **parked** order (`geoFail` → 📍 fix address, `geoAmbig` → ⚠ pick a town)
keeps its last-known pin, because `route.js` never blanks one, and that pin is precisely
the one already known to be in the wrong place. So `destOf` gates the coordinates on
`isParked(item)`, not on `coordsOf(item)` alone, and a flagged order still navigates by its
address. Reusing `isParked` rather than writing a fresh geoFail/geoAmbig test is the point:
there is one answer in this repo to "may the truck be routed on this pin", and the navigate
path is now a caller of it instead of a second opinion.

**The clipboard half is untouched.** `addressLabel()` still copies the card's unit +
address line, still synchronously inside the tap handler and still before the iOS scheme
hand-off — the destination string, which may now be a bare `lat,lng`, never reaches the
clipboard (asserted). The three URLs downstream needed no change at all: `daddr=` and
`destination=` take a coordinate pair as happily as a street.

Two things deliberately left alone, so the next agent knows they were seen: the card's 🧭
only renders when `item.address` is set, which is still right because pins come *from*
forward-geocoding the address (a pin with no address is not a state a real order reaches);
and `js/drive.js`'s `driveNav.disabled` gate reads `item.lat && item.lng` by truthiness
rather than through `coordsOf`, which differs only for junk coordinates on an order that
also has no address.

`tests/worklist-directions.test.mjs` pins all three properties — pin before address,
`isParked` in the gate, address-not-coordinates on the clipboard — as source-shape
assertions, since `worklist.js` is DOM-bound and `node --test` cannot import it. No `sw.js`
CACHE bump: no new module or stylesheet, only edits to files already in `SHELL`.

Then driven end-to-end in headless Chromium (`VERIFY.md` §3, every non-localhost request
aborted at the browser so nothing could reach the production Sheet), with `window.open` and
`navigator.clipboard.writeText` stubbed to record their arguments: **8/8** — four seeded
orders (clean pin, `geoFail` + pin, `geoAmbig` + pin, no pin) pressed on the worklist's 🧭
and again on the Drive screen's **Navigate**, both surfaces identical. The clean order
opened `…&destination=45.3311%2C-79.2117`; all three others opened
`…&destination=<address>%2C%20ON`; every one of the eight copied the card's own address
line. Worth knowing for the next drive: a `page.goto` that differs only in the `#hash` is a
**same-document** navigation, so seeding `localStorage`/IndexedDB and then "reloading" into
`#worklist` leaves the un-seeded modules — and the auto-opened settings sheet — in place,
covering the list; add a throwaway query string to force a real load.
