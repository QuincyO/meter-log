# 2026-08-10 — A J# field cleans up after the scanner: a bad scan wipes itself, a re-scan replaces instead of appends

The crew captures Old/New J# by scanning a barcode. The phone's scanner is a keyboard
wedge — it types straight into whichever field is focused — so scanning a second time
**appends** to the first value, and fixing a mis-scan meant tapping into the field,
selecting all, and backspacing before scanning again. The ask: *"if I scan it, it knows it
was the wrong format and it just deletes the text anyways and then allows me to scan it
again"* — and explicitly **no button to press, no wrong-format popup**.

## The four J# fields self-normalize on every input

`js/jnumber.js` (new), `tests/jnumber.test.mjs` (new), `js/pages/capture.js`, `sw.js`,
`tests/cache-refresh.test.mjs`, `tests/drag-autoscroll.test.mjs`,
`tests/installer-metrics-cache-docs.test.mjs`

A J# is always `J` + exactly 7 digits (e.g. `J1234567`). One stateless rule, run on every
`input` event over `installOldJ`, `newJ`, `oldJ`, `otherOldJ`, delivers everything the crew
asked for with no button and no popup:

> uppercase, anchor on the **last** `J`, keep `J` + up to 7 digits after it.

- **Wrong barcode** (a UPC or any code with no valid `J#######`) normalizes to `''` → the
  field **wipes itself**, visibly ready to scan again.
- **Re-scan onto a wrong value** → the fresh scan's `J#######` is the *last* `J`, so it
  **wins**: `J1234567J7654321` → `J7654321`. Replace, never append — which is what makes the
  no-button workflow possible.
- **Correct scan / manual type** → `j1234567` → `J1234567`; a partial `J12` is a valid
  prefix and is left alone as you type. Trailing newline/CR from the scanner is absorbed.

Two small companions on the same fields: `focus` selects the whole value (tap once and the
next scan overwrites, if you ever want to redo by hand), and a keydown handler swallows the
scanner's trailing **Enter** so focus stays put for back-to-back scans (there is no `<form>`
here to submit). Programmatic prefill (`fillCapture`) sets `.value` directly and fires no
`input`, so planned-order fills are untouched.

**Trap worth remembering:** the whole thing works *because* it anchors on the **last** J,
not the first. Anchor on the first J and an appended re-scan keeps the stale value and drops
the new one — the exact opposite of what the crew wants. It also means a wrong scan that
happens to contain its own `J`+7-digits substring would be read as that substring; real
UPC/other barcodes are numeric, so this doesn't bite in the field. The rule is a pure
function (`normalizeJScan`), so it lives in `node --test` rather than in the DOM.

**Deliberately not done:** no save-time format toast (the crew asked for no popup — the live
rule already guarantees `J`+≤7-digits or empty, and the existing *New J# is required*
presence check stays); and the edit-card / worklist / look-up J# inputs are left alone — the
scope was the four capture fields.

## Verification

`node --test "tests/*.test.mjs"` — 485/485, including 11 new cases in `jnumber.test.mjs`
(wipe-on-no-J, append→newest-J-wins, 8th-digit dropped, leading noise, trailing CR, partial
prefix kept). Also driven headless against a real DOM (VERIFY.md §3): a lowercase scan lands
`J1234567`, a numeric barcode empties the field, an appended re-scan resolves to the newest
J, a trailing CR is absorbed, and focus selects the whole value. Frontend-only, no write
path touched, so nothing reaches the production Sheet. `sw.js` ships the new module
(`CACHE` bumped v38 → v39, the three pinned version tests bumped alongside it).

# 2026-08-10 — The daily-log PDF's blank bottom now prints the day's notes

The end-of-day PDF is drawn top-down — header grid, table, totals — and then simply stops,
so the bottom of the page is white space. Meanwhile the app captures three kinds of
free-text note that never appeared on the sheet at all. The ask: *"in the blank space of
the PDF … if I created notes for downtime or I created end of day notes, that blank space is
where the comments should be."*

## Notes now print in the blank space of the daily-log PDF

`js/dailylog.js`, `js/pages/capture.js`, `Code.gs`, `tests/daily-log-notes.test.mjs` (new)

A **Notes** block now fills the blank area under the totals on both templates (boat and
land). `collectNotes(summary)` (a pure, exported, unit-tested function) gathers the day's
remarks in reading order — **end of day** first, then **downtime** notes, then **per-stop**
notes — and `drawNotesBlock` wraps each to the page width with a bold `Label:` lead, page-
breaking like the row loops. The stop and downtime rows already ride in the summary the
renderer consumes, so no new read plumbing.

- **The downtime `note` column is overloaded**, and that is the one trap in the render half.
  The EOD travel review writes `gap HH:MM–HH:MM` machine tags into the same column
  (`saveTravel`) to attribute a deduction to a WO→WO gap. Those are not human remarks, so
  `collectNotes` skips any note matching `/^\s*gap\s+\d/i`. The test pins it: a
  `gap 09:10–09:25` row must never reach the block.
- **The end-of-day note needed a client overlay** — the same shape as the [bookend
  trap](2026-07-24.md). `buildDaySummary` reads `notes` only from the request body, and the
  online PDF paths don't carry it: `previewDailyLog` (capture + edit `genLog`) omits it, and
  the close-time prefetch runs *before* the note is typed. The offline path already passed
  `$('eodNotes').value`; the fix sets `summary.notes = $('eodNotes').value.trim()` on the
  client right before each `downloadDailyLog`, so the freshest typed note always wins
  regardless of which summary (server / prefetch / cache) was chosen. Downtime and per-stop
  notes are persisted before close and need no overlay.
- **Editor reprints pull the saved note.** So regenerating a past day's PDF from `edit.html`
  matches the original, `buildDaySummary` now falls back to the persisted `Tracker` row's
  `notes` when the request omits the field — guarded on `b.notes != null`, *not* truthiness,
  so a note deliberately cleared during a live close is still respected (the same rule the
  bookend fallbacks use).

**Deliberately kept in scope:** all three note kinds print (the user chose to include
per-stop notes, which had no home on the sheet before). No layout constants moved; the block
is additive after the totals, so a full-page day just flows the notes onto a second page.

## Verification

`node --test "tests/*.test.mjs"` — the new `daily-log-notes.test.mjs` covers `collectNotes`
(all three note kinds collected, gap machine-tag excluded, empty in → empty out) and text-
guards that both templates call `drawNotesBlock` and that capture overlays the typed note
before render. `collectNotes` is DOM-free and imports cleanly under `node --test`. Manual
(VERIFY.md headless drive, write paths kept off the production Sheet): a stop note, an
`OTHER` downtime note and an end-of-day note all print under a **Notes** heading in the
previously-blank area, in both land and boat modes and offline; a `gap …` travel row does
not leak in; and an `edit.html` reprint of a closed day shows the saved end-of-day note.

# 2026-08-10 — The analytics page finally shows the InstallerMetrics tab

The spine has been rolling up per-installer lifetime analytics into `InstallerMetrics`
since July — days/hours worked, installs, pace, the boat/land splits, the dwell model the
route planner prices ETAs with — and the phone and planner read slices of it, but the
office's analytics view never showed any of it. The ask: surface the installer metrics on
the analytics page, plus whatever can usefully be derived from them.

## Installer lifetime metrics — a new section on map.html's Analytics view

`js/compute/installer-lifetime.js` (new), `tests/installer-lifetime.test.mjs` (new),
`js/pages/map.js`, `map.html`, `css/map.css`, `sw.js`, `tests/cache-refresh.test.mjs`,
`USER-GUIDE.md`

Three cards below the existing windowed charts, fed by one wide
`?action=installerMetrics` read (no `workType`, so the combined + `boat*` + `land*`
column groups all arrive):

- **Lifetime by installer** — days, hours, logs, installs, UTIs, plus the derived rates
  (UTI %, downtime min/day, hours/day) and the sheet's own avg/day, avg/hr, avg log
  minutes. The Recent-30 column carries a pace-trend glyph — ▼ recently faster than
  lifetime, ▲ slower, plain when inside a steady band of max(2 min, 10%) so ordinary
  jitter (31 vs 32) never paints an arrow. Rows with `daysWorked` 0/blank are dropped
  (a roster entry that has never closed a day is not a metric).
- **Avg minutes per log — land vs boat** — grouped bars per installer, the starkest
  derived story in the data (land runs ~2–3× faster: 20 vs 53 min and 16 vs 48 min for
  the two main installers). An installer missing a mode gets a null, which Chart.js
  skips rather than drawing a zero.
- **Dwell model (feeds route ETAs)** — on-site minutes, +min per extra meter, travel
  min/km and a source badge (`gps`/`fit`/`pace`) per installer, so the numbers behind
  the planner's ETAs can be sanity-checked at a glance. Rows with no dwell evidence at
  all are dropped — `pace` alone means "still guessing", which isn't worth a row.

**The section is honestly lifetime.** The `installerMetrics` read has no from/to window —
the tab is all-time rollups rebuilt at end of day — so the section says so in its caption
instead of pretending the page's date range applies. The installer chips *do* filter it
(client-side by name: the tab is H-number-keyed but carries the roster name on every row,
which is what makes the join to the name-keyed chips free). The fetch is lazy and
memoized: first analytics render pulls it once, range changes re-filter without refetching,
and a failed fetch resets the promise so the next render retries.

**Trap worth remembering:** every number off this tab must pass through a `'' → null`
guard (`num()` in the compute module) — blank sheet cells arrive as empty strings, and
`Number('')` is `0` while `Number(undefined)` is `NaN`, either of which silently poisons
an average. The shaping lives in `js/compute/installer-lifetime.js` precisely so
`node --test` pins that behaviour without a DOM.

## ⓘ explainers on each lifetime card

`map.html`, `js/pages/map.js`, `css/map.css`, `tests/installer-lifetime.test.mjs`,
`USER-GUIDE.md`

Follow-up in the same day: the cards are full of jargon nobody should need this repo to
decode — *what's a dwell model, what's the difference between `fit` and `pace`, how is one
calculated versus the other?* Each card's `h3` now carries a small ⓘ button that toggles an
inline plain-language infobox: the lifetime table's column definitions (what Avg log
measures, what the ▼/▲ arrows compare), why the land-vs-boat split is compared
per-installer, and — the one that prompted the ask — what On-site / +Per meter / Travel
mean and how each **source** is measured (GPS = stop gap minus the real recorded drive;
FIT = a line fitted through stop-to-stop gaps against distance, intercept = on-site,
slope = travel; PACE = not measured yet, still the generic guess). It's an inline box
rather than a hover tooltip because the office reads this page on phones too — hover
doesn't exist there, a tap does. Text lives in `map.html` markup, not JS strings; the test
pins that every card has a button + box and that the dwell box explains all three sources,
so a new source badge can't ship unexplained. No new file, so no `CACHE` bump —
stale-while-revalidate ships edited files on the next open.

## Verification

`node --test "tests/*.test.mjs"` — all green including 12 new cases in
`installer-lifetime.test.mjs` (zero-day rows dropped, `''` → null never NaN, string

# 2026-08-10 — A GPS dwell sample now requires a log inside the parked hole

`Code.gs`, `tests/dwell-measure.test.mjs`, `ARCHITECTURE.md`, `AGENTS.md`, `map.html`,
`USER-GUIDE.md`

While reading the new dwell card the user asked the right question: *"is the qualifying
gap validated when a log happens inside of that gap?"* It wasn't.
`installerOnSiteFromTracks` counted **any** 2–120-minute hole between two recorded
driving legs as time installing — which is also exactly what lunch, a coffee stop and a
supply run look like. The median absorbs those once there's volume, but the evidence bar
is only 15 samples (`DWELL_MIN_TRACK_SAMPLES`), and a freshly-qualified GPS number
immediately **outranks** a fit built from hundreds of stop-to-stop gaps — so the moment
contamination matters most is the moment there's least data to dilute it.

A parked hole now counts only when one of the installer's own printable logs
(INSTALLED/UTI/VISITED/UNACCOUNTED) has a timestamp inside it, plus a 2-minute
pull-away grace (`DWELL_TRACK_LOG_GRACE_MIN`) for the ordinary drive-off-then-tap. Two
deliberate scope choices: the validating log is **not** mode-filtered (the leg pair
already fixes the sample's mode, and a mis-tagged log is still proof the parked time was
a job), and walk-up jobs need nothing special — they have logs like any other stop.

**The live data made the case before the code shipped.** Of the 6 qualifying gaps in the
production `DriveTracks` (all Quincy's), only **1** contains a log — the other 5 sit on a
morning stretch of 2026-07-24 that ends almost an hour before the day's first log, i.e.
they were never installs at all. Under the old rule those 5 were a third of the way to a
contaminated GPS median.

**Trap worth remembering:** the first fixture for "no log in any hole" shifted log
minutes with `(m + 30) % 60` and no hour carry, which quietly dropped some logs into
*neighbouring* holes — the test passed, but for a murkier reason than its comment
claimed. Fixtures that place times relative to a window need the arithmetic done on the
full clock, not the minute field.

## Verification

`node --test "tests/*.test.mjs"` — the two existing GPS tests updated (their fixtures
now carry logs inside the holes) plus two new: every-log-mid-drive yields `''` (18
unvalidated holes report nothing), and a log 1 minute after pull-away still validates
via the grace. Cross-checked against production data (nightly `data/Stops.md` export +
the `DriveTracks` tab): the new rule keeps 1 of the current 6 samples, dropping exactly
the five holes with no log anywhere near them. Spine-only change — CI deploys `Code.gs`
on push, no schema change, no `setupSheets()`; the stored dwell numbers recompute at the
next end-of-day close (all sources currently `fit`/`pace`, and with 1 < 15 samples that
is unchanged, so nothing visible moves until real log-validated recording accumulates).

# 2026-08-10 — The recorder splits a leg at every real stop, and a dwell sample must be near the address

`js/drive-track.js`, `js/drive-recorder.js`, `Code.gs`, `tests/drive-track.test.mjs`,
`tests/dwell-measure.test.mjs`, `sw.js` (v40 → v41 + the three pinned tests),
`ARCHITECTURE.md`, `AGENTS.md`, `map.html`

Following the log-inside-the-hole rule, the user described their plan for feeding the
GPS dwell model — leave the phone recording in the car, log each stop, navigate on —
and checking it against the recorder exposed a design mismatch: **a recorded day was
deliberately ONE continuous leg** (nothing split at a stop; backgrounding bracketed
in-leg gap anchors; even an OS kill rejoined the same leg), so the between-leg parked
holes `installerOnSiteFromTracks` measures **never existed** in normal use. The
2026-08-05 recording was the live proof: one three-hour leg, zero samples, however
faithfully the crew recorded.

## Legs are park-to-park now — `stillCheck` splits at each stop

`stillCheck()` (pure, in the track model, unit-tested) watches kept points for a
stationary episode: anchor on the first at-or-below-idle-speed fix, hold while every
fix stays within `STILL_RADIUS_M` (40 m), and when the truck finally moves off after
at least `STILL_SPLIT_MS` (2 min), report the **arrival index**. The recorder ends the
old leg there — its `endTime` is the arrival the dwell model reads — starts the new
leg at the departure fix, and drops the parked jitter between them. A background gap
while parked stretches the episode (no fixes arrive, the anchor holds, the resume fix
lands inside the radius); a red light is under the bar; a drive-thru queue can fire
and the log-validation rule discards it. The anchor rides `raw.still` through
checkpoints so a cold-start mid-park keeps the episode. The cold-start **rejoin**
still rejoins the open leg — one leg per *drive* now, not per day.

## And the validating log must be near the parked truck

Mid-build the user asked for one more check: *"can we add a check to see if we're
close to the address?"* Time alone can't tell "parked at the job" from "parked at the
depot while a log happened across town", so the spine now also requires the
validating log's own pin to sit within `DWELL_TRACK_NEAR_M` (**300 m**) of where the
truck parked — the previous leg's last polyline point, decoded by
`driveTrackLastPoint`, a hand port of `decodeTrack`'s delta walk (Apps Script can't
import the module; the test suite feeds it strings built by the real `encodeTrack`,
so the two can't drift silently). Deliberate scope: the stop's **logged pin**, not
the geocoded address (the pin is where the crew actually stood); 300 m is generous
because rural driveways run long and the recorder phone sits in the car while the
installer walks to the meter; and the check **skips itself** when a leg has no
polyline or a stop no pin — a tightener, never a sample-killer, so legacy rows keep
counting.

**Trap worth remembering:** the first no-log-in-any-hole fixture shifted log minutes
with `(m + 30) % 60` and no hour carry, which dropped some logs into *neighbouring*
holes — the test passed for a murkier reason than its comment claimed. Fixture times
need arithmetic on the full clock, not the minute field.

## Verification

`node --test "tests/*.test.mjs"` — four new `stillCheck` cases (splits at the arrival
point exactly once; a 1-minute light never fires; parked jitter inside the radius
holds one episode; a background gap while parked still splits) and two new spine
cases (a log 2 km from the parked truck validates nothing; no-polyline legs and
pinless stops skip the proximity check and keep their samples). Full suite green.
Push deploys both halves — Pages ships the recorder, CI redeploys `Code.gs` — and the
`CACHE` bump ships the new recorder to phones on next open. Nothing visible changes
until log-validated, address-near samples accumulate past the 15 bar; from tomorrow,
a normally recorded + logged day produces roughly one sample per stop, so ~2 days
flips `onSiteSource` to `gps`.
