# 2026-07-29 — Optimize needs the district; a duplicate J# warns instead of discarding; the Drive screen refreshes itself

## A pack-less Optimize tap no longer routes crow-flies in silence

`js/worklist.js`, `js/pages/capture.js`, `index.html`, `css/capture.css`,
`tests/worklist-optimize-gate.test.mjs`, `ARCHITECTURE.md`, `AGENTS.md`, `USER-GUIDE.md`

Asked for directly: on the worklist screen, **the district has to be downloaded before
anyone can optimize**. The planner is explicitly excluded.

Until now a tap on 🧭 Optimize ran either way — the district pack when the phone had one,
**straight-line distances when it didn't**. That fallback is the problem. It produces a
route that looks solved and is blind to every river, dead end and bridge, and nothing on
screen says which one you got: the same button, the same progress line, the same numbered
pins. A crew can drive a whole day off it without ever learning the map was never
downloaded.

So `optimizeRouteHandler` refuses the tap outright when `installedPacks()` is empty, and
the refusal names the fix — *Download your district first — Settings ▸ Offline road map*.

**The two-second hold is deliberately exempt**, and that is not an oversight to tidy up
later. It skips the pack by design (`opts.noLocalGraph`) and asks a router that has the
turn restrictions the pack does not, so it is the only second opinion a suspect on-device
route has. Gate it too and a crew with a wrong-looking route has nothing to check it
against. It still needs signal, and the offline refusal for a hold on a phone with no
district now points at the download rather than at a tap that would no longer work.

## Saying so before anyone presses it

`paintOptimizeGate` greys the button (`#wlOptimize.gated`), sets `aria-disabled`, and
prints the reason in a new `#wlOptimizeGate` line underneath. Two things are load-bearing
and both are pinned by tests:

- **It must never set `btn.disabled`.** A disabled button fires no pointer events at all,
  which would kill the hold — the one press that legitimately still works — along with the
  tap's own explanatory toast. Greying is CSS opacity plus `aria-disabled`, and the rule
  deliberately carries no `pointer-events:none`. That property on this button belongs to
  the run in flight, which sets it while a route is being worked out.
- **The gate reads `installedPacks()`, never `activePackId()`** — the standing rule from
  2026-07-26, and it bites harder now that the same test decides whether the button works
  at all rather than only what the confirmation sheet says.

**The repaint hole worth remembering:** the ☰ nav lives *outside* `captureMain`, so
Settings opens **over** the worklist screen and closes again without that screen ever
re-rendering. Downloading a district would have left the crew looking at a greyed button
still telling them to download one. `paintRoadPacks()` — the single place both the
download and the delete funnel through — now calls `paintOptimizeGate()`, which is why it
is exported. The delete confirmation stops promising "routes go back to straight-line
estimates" too, because they don't: Optimize stops working on that phone.

The dead branches went with it — the tap can no longer be pack-less, so the
"straight-line algorithm" line in the pre-run sheet is gone and a tap always announces
*offline road map on this phone*.

## A duplicate J number warns the installer — and never costs them the stop

`js/jdup.js` (new), `js/pages/capture.js`, `Code.gs`, `index.html`,
`css/capture.css`, `sw.js`, `tests/jdup.test.mjs` (new),
`tests/jdup-parity.test.mjs` (new), `tests/stop-never-discarded.test.mjs` (new),
`ARCHITECTURE.md`, `AGENTS.md`, `USER-GUIDE.md`

Asked for directly: when a stop is logged and the **New J#** or the **Old J#** matches
something already logged, tell the installer and point at the order it's already on.
Never delete a stop over a duplicate — the installer makes the correction by hand.

**The second half of that was already being violated, quietly.** `addStop` matched on
the *work order*, not the J number, and on an exact WO#+New J# hit it did this:

```js
if (history.some(r => norm(r.newJNumber) === norm(b.newJNumber))) {
  return { ok: false, duplicate: true, history: history };   // before appendRow
}
```

— returned **before** `sh.appendRow(row)`, and the phone rendered *"Duplicate — WO# … with
J# … was already logged. **Entry discarded.**"* A real stop, destroyed, at the moment the
crew is least able to notice it happened. That path is gone. The row is appended first,
always; the warning rides back on an ordinary `{ok:true}` ack as `res.jConflicts`.
`tests/stop-never-discarded.test.mjs` fails the build if an early return ever reappears in
`addStop` before the append — the rule is CI-enforced now, not remembered.

### The rule, and the two shapes it deliberately ignores

`js/jdup.js` is pure and DOM-free (`jConflicts(candidate, stops, {from, installer})`),
scoped to **this installer's own stops over the last 7 days** — which is exactly what
`loadRecentDays(7)` already holds in IndexedDB, so the phone needed no new storage and the
check works with no signal.

Matching is **same-field only** — New J# against New J#, Old J# against Old J#, never
across the two. That is not tidiness: a meter installed at one house and legitimately
pulled out of another later carries the same serial in *both* columns by design, so
cross-matching would flag every ordinary swap. And **a blank J# never matches** — every
UTI has a blank New J# and most rows a blank Old J#, so blank-vs-blank would flag the whole
week. Either one trains the crew to dismiss the card, which costs more than not having it.

One carve-out, for the same reason: **an Old J# repeated on the SAME work order is not a
conflict.** That is the revisit — a UTI records the old meter's serial, the crew comes back
and installs, same site, same meter, two correct rows. Without it every revisit would block
the log. Nothing is lost, because two real installs on one order still surface through the
New J# rule (same meter) or the WO#-keyed `flagged` warning (different meter); an Old J#
across two *different* orders — the actual mistype — still fires.

### Two checks, because one of them can't be both instant and complete

**On the phone, before the stop is sent:** a hit blocks the **Log stop** tap and shows the
`#jConflict` card naming the order the number is already on — *Go back and fix it* /
*Log it anyway — both stops are kept*. The entry stays in the form either way.

The index it reads is **preloaded into `recentJStops` rather than awaited inside the
handler**, and that is load-bearing: `$('logStop').onclick` has to stay synchronous or the
plan-mode WO# clipboard copy loses its user gesture. An `await` before `enqueue` would
break the copy silently.

**On the spine, on the ack:** `jConflictsFor` sees what the phone can't — a J# a crewmate
logged from another device. Surfaced as the amber notice banner, which unlike every other
notice does **not** auto-dismiss, because it's something to act on, and is suppressed when
the card already asked about that exact entry (`jSignature`).

`Code.gs` carries a hand copy of the four rule functions, since Apps Script can't import an
ES module. `tests/jdup-parity.test.mjs` evaluates the real `Code.gs` source and holds both
to the same output over one case table — without it the two drift silently and the feature
just behaves at random. **Change one, change the other.**

No schema change: no new `Stops` column, so no `setupSheets()` re-run. `sw.js` bumps to
`meterlog-v39` and ships `js/jdup.js`, which is a hard import of `capture.js` — missing
from the shell it isn't a degraded warning, it's a capture page that won't load offline.

### Verified

513 unit tests, then the real page driven headless with every spine POST intercepted
(VERIFY.md §4), against a seeded week: the card fires on a duplicate New J# and names
WO# 1000 · 12 Bay St; *Go back and fix it* leaves both fields intact and queues nothing;
typing a new J# drops the card; *Log it anyway* queues the stop; a same-order Old J#
revisit doesn't interrupt; the same Old J# on a different order does; and all of it still
fires with the browser switched offline.

## The Drive screen keeps itself current while you drive

`js/drive.js`, `js/worklist.js`, `index.html`, `USER-GUIDE.md`,
`tests/drive-auto-refresh.test.mjs`, `tests/pace-live.test.mjs`,
`ARCHITECTURE.md`, `AGENTS.md`

Asked for directly: **automatic refreshes from the sheet on the Drive page, every five
minutes — but only while you're driving, only if you've agreed to see your driving
stats, and only while you're actually on that screen.**

Nothing on that screen was ever on a clock. The only thing that made it repaint was the
GPS recorder's `subscribe()`, which fires once per fix — so the moment fixes stopped, the
card and the arrival times froze at whatever they last said. Opening Google Maps to
navigate backgrounds the PWA and stops the fixes; so does a denied GPS permission, or
simply not recording. The only way to unfreeze them was to leave Drive mode, go back to
the worklist, and tap ⇩ Download. That is a lot of taps at 80 km/h to answer "am I still
on track".

So `js/drive.js` runs an interval while the screen is open and refreshes on a **5-minute**
throttle. Three gates, all required, all of them the ones asked for: drive tracking armed
(`isRecording()` — the per-day per-phone opt-in), the **Show driving stats** switch on,
and the Drive screen in front; plus not backgrounded and online, which the network
demands. The interval ticks every 30 s, but that is retry granularity and **not** the
period — the five minutes live in a timestamp throttle, so a tick that lands while the
driver is in Maps costs seconds of staleness instead of a whole further period. Opening
the screen counts as "never synced", so the first tick refreshes at once; the stamp is
deliberately not reset by `open()`, because the crew hops between the worklist and this
screen constantly and a re-entry inside the window must not re-fetch.

**The half that actually fixes the times isn't the download.** The report behind this was
"the expected route and time only get accurate when I pull from the worklist", and that is
exactly right — but not for the reason it looks like. Nothing in the pull rewrites
`order`/`day`/`scheduledEta`. **`applyTodayAnchor()` does**, by re-running
`scheduleRouteConstraints` from where the crew is now, and ⇩ Download happens to end with
it. A plain day-cache refresh — which is what the existing GPS-driven pull did — moves the
pace gauge's `done` count and nothing else, which is why it was already running every
three minutes and the times still read stale. `autoSync` therefore does all three:
the list, then `cacheRecentDays(1)`, then the re-anchor. `PACE_REFRESH_MS` goes 3 → 5 min
to match, so the two pulls share one period instead of being two clocks disagreeing about
how fresh "fresh" is.

**An unattended refresh is not a Download with the prompts removed**, and the differences
are the whole risk surface. A locally-**done** order must never come back: `syncWorklist()`
pushes the phone's list up only right after a log and no-ops offline, and nothing re-runs
it on reconnect — so a stop logged in a dead zone leaves the sheet's row saying `pending`
long after the meter reached `Stops`. The manual Download resurrecting it is a visible
mistake the installer asked for; a timer doing it silently sends the crew back to a house
they already did. Hence `preserveDone` on the automatic path only (collected *before* the
local store is wiped), and the pull is skipped outright while the offline queue is
non-empty, since an un-drained queue means the phone is ahead of the sheet. Three more:
no `toast` and no `confirm` — nobody answers a modal at 80 km/h, and "check signal"
popping every five minutes through a dead zone is worse than the staleness it reports, so
every failure keeps the last good copy and says nothing; no `savePlan` push; and no
`planAdvance()`, which ends in `fillCapture` and would let a background timer overwrite a
half-typed capture form. The `refresh()` that follows also re-matches the card by
`destKey`, so a re-ordered route can't swap the house under the driver mid-drive.

**The stats toggle is now a consent gate, not just a HUD switch** — it decides whether the
app fetches, not only whether it displays — so its hint in Route tuning and the user guide
say so. A gate the driver can't read isn't consent.

The normalizer that turns a sheet row into a local record is shared by both paths now
(`applyDownloadedList`), so the manual and automatic landings can never drift apart.
No new module, so no `sw.js` bump.

### Verified

522 unit tests, then the real Drive screen driven headless with every request outside
`localhost` blocked at the browser and the spine stubbed (VERIFY.md §3–4), on a controlled
clock: 17/17. The truth table holds — tracking off, stats off, or navigated away all fetch
nothing, and neither does a backgrounded tab; with all three on it fetches exactly once
per five minutes and never twice in flight. An order added by the office lands on the card
within one period, the re-anchor writes arrival times onto orders that shipped without
them, the driver's own card doesn't move underneath, an order marked done locally stays
done through a refresh, and leaving `#drive` clears the interval so nothing fetches after.
No write action ever reached the spine.
